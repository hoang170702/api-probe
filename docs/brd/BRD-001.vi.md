## 1. Mục tiêu

Tool giúp **tester** kiểm thử một API bằng nhiều bộ dữ liệu mà không cần viết code:

1. Tester dán một lệnh `curl` (ví dụ copy từ Postman hoặc Chrome DevTools).
2. Tool tách ra method, URL, headers, body và **liệt kê các field** trong JSON body.
3. Với mỗi field, tester chọn **Required** hoặc **Unrequired** (dropdown).
4. Ngay dưới curl, tester nhập **N test case** vào một bảng chỉnh sửa được, bấm **`+`** để thêm mỗi dòng mới; mỗi case có một mã **expect** phải xuất hiện trong response (§8).
   Khi API cần token, tester thêm các **bước chuẩn bị** tuỳ chọn (ví dụ một curl login); token chúng trả về được tự động gắn vào curl chính (§11.3).
5. Tool **bắn** từng bộ, mỗi bộ chạy trên **1 goroutine** qua worker pool có giới hạn.
6. Trả kết quả **realtime** cho tester: `SUCCESS` (tìm thấy mã expect trong response) / `FAILED` (không tìm thấy) / `EXCEPTION` / `BLOCKED`.
7. Tester **xuất báo cáo** Excel hoặc PDF.

### Ngoài phạm vi (v1)

- Không có database. Mọi dữ liệu của một lần chạy (run) nằm trong bộ nhớ và hết hạn sau TTL.
- Không Kafka, Redis, microservices; không đăng nhập hay quản lý user.
- Không phải công cụ load test. Concurrency bị giới hạn có chủ đích.
- Không retry tự động (xem §11.2; đây là biện pháp an toàn cho API payment).
- v1 chỉ hỗ trợ body **JSON**. `form-urlencoded`, `multipart`, file upload để sau.

| D12 | FE: **React + TypeScript + Vite + Ant Design**. BE: một monolith duy nhất. |
| D13 | Ngôn ngữ BE: **Go** (chốt từ OD1). Thư viện theo §3.1. |
| D14 | Pass/fail chỉ dựa trên **mã expect** (v0.7; thay cho quy tắc 2xx đã chốt từ OD2; cách so status chỉnh ở v0.8). Mã chỉ khớp HTTP status khi nó **chính là** status code (`401` ↔ HTTP 401); ngoài ra mã được tìm, phân biệt hoa thường, trong toàn bộ body đã đọc (tối đa 1 MB) rồi trong mọi header của response dạng `Name: value`, trừ các header kỹ thuật (`Date`, `Content-Length`, `Content-Type`, `Server`, `Connection`, `ETag`, `Last-Modified`, `Expires`, `Cache-Control`, `Vary`, `Transfer-Encoding`, `Keep-Alive`, `Age`), vì giá trị của chúng dễ khớp nhầm với mã ngắn. | D16 | Test case **chỉ nhập trên UI**: sau khi Analyze, cấu hình hiện ngay dưới curl, bấm **`+`** để thêm một dòng đánh số (`1.`, `2.`, `3.` …) gồm một cột cho mỗi field và cột `expect` (§8). Không sinh hay import file test data. |
| D17 | Tên service: **API Case Runner** (module `caserunner`, tiền tố env `CASERUNNER_`), thuộc dự án APIProbe (chốt từ OD3). |
| D18 | Backend theo **Clean Architecture**: `domain` ← `usecase` ← `adapter`, nối với nhau ở `cmd/caserunner` (§14). |
| D19 | Bản build FE được **nhúng vào binary Go**: một file chạy duy nhất phục vụ cả giao diện lẫn API (§21). |
| D20 | **Bước chuẩn bị là tuỳ chọn.** Khi API cần token, tester thêm một hoặc nhiều curl chuẩn bị (login, OTP, …). Chúng chạy theo thứ tự; mỗi bước **bắt** giá trị từ response vào biến (token được tìm tự động, hoặc theo path tester chỉ định). Curl chính tự được đặt `Authorization: Bearer {{token}}` (tắt được), và có thể dùng `{{name}}` ở bất kỳ đâu trong URL, header hay body của curl chính và của các bước sau (§11.3). |
| D21 | Khi có bước chuẩn bị, các case chạy **lần lượt từng case**, và các bước chuẩn bị chạy lại **trước mỗi case**, nên mỗi case dùng một token mới. Không có bước chuẩn bị thì case chạy song song như D6. |
| D22 | Giao diện có **tiếng Việt và tiếng Anh**, đổi ở đầu trang; lựa chọn được trình duyệt nhớ, lần đầu theo ngôn ngữ của trình duyệt. Thông báo từ backend (lỗi parse, cảnh báo, reason) vẫn bằng tiếng Anh. |

### 3.1 Thư viện Go (D13)

| Hạng mục | Lựa chọn |

| Tách curl | tự viết tokenizer (§6) |
| Đóng gói | một binary; bản build FE được nhúng bằng `embed` (D19) |

OD1 (Go hay Java), OD2 (tiêu chí pass/fail, định nghĩa lại ở v0.7) và OD3 (tên) đã chốt thành D13, D14–D15 và D17; OD4 chốt như bảng dưới.

## 6. Curl Parser (đặc tả)

Package `domain/curl`. Không bao giờ chạy shell và không bao giờ expand `$VAR`.

### 6.1 Input

Chuỗi lệnh curl, có thể nhiều dòng, xuống dòng kiểu LF hoặc CRLF. Hỗ trợ cả hai kiểu copy:
- **bash** (Chrome/Firefox "Copy as cURL (bash)", Postman, viết tay).
- **Windows cmd** (Chrome "Copy as cURL (cmd)").

Kiểu được nhận diện qua ký tự nối dòng: dòng kết thúc bằng `^` là cmd, kết thúc bằng `\` là bash. Lệnh chỉ có một dòng thì là cmd nếu chứa `^"`, còn lại là bash.

Từ đầu tiên phải là `curl` hoặc `curl.exe` (không phân biệt hoa thường).

### 6.2 Tokenizer

**bash:**
- `\` + xuống dòng là nối dòng và bị bỏ đi.
- Trong `'...'`: giữ nguyên tuyệt đối.
- Trong `"..."`: bỏ escape cho `\"`, `\\`, `\$` và `` \` ``; `\` + xuống dòng bị bỏ đi; dấu `\` khác giữ nguyên.
- Trong `$'...'` (Chrome dùng khi body có `'` hoặc xuống dòng): escape kiểu ANSI-C `\n \t \r \a \b \f \v \e \\ \' \" \?`, `\xHH`, `\uHHHH`, `\UHHHHHHHH` và bát phân `\nnn`.
- Ngoài quote: `\` escape ký tự kế tiếp; khoảng trắng tách từ. Các phần có quote và không quote nằm sát nhau ghép thành một từ; `''` là một từ rỗng.

**cmd** đi qua hai lớp mà Windows áp dụng:
1. cmd.exe: bên ngoài cặp `"..."` của chính nó, `^` + xuống dòng là nối dòng, và `^x` thành `x`.
2. curl.exe tách tham số (quy tắc `CommandLineToArgvW`): ngoài quote thì khoảng trắng tách từ; `"` bật/tắt quote; 2n dấu `\` trước `"` thành n dấu và quote đổi trạng thái, 2n+1 dấu thành n dấu cộng một `"` thật; `""` trong quote là một `"` thật; các dấu `\` khác giữ nguyên.

### 6.3 Flag

Flag ngắn có thể gộp (`-sSLk`) và nhận giá trị dính liền (`-XPOST`, `-H'X: 1'`). `--` kết thúc phần flag.

| Flag | Xử lý |
|---|---|
| `-X`, `--request` | method, giữ nguyên như đã viết |
| `-H`, `--header` | header `Name: value` (giữ thứ tự, cho phép trùng tên). `Name;` gửi header rỗng. `Name:` ("xoá header này" của curl) và giá trị không có `:` bị bỏ qua kèm cảnh báo. `@file` → `CURL_UNSUPPORTED` |
| `-d`, `--data`, `--data-ascii`, `--data-binary` | một phần của body. Giá trị bắt đầu bằng `@` (đọc từ file) → `CURL_UNSUPPORTED` |
| `--data-raw` | một phần của body; dấu `@` ở đầu là chữ thường, đúng như curl |
| `--json` | một phần của body; thêm `Content-Type: application/json` và `Accept: application/json` nếu tester chưa đặt. `@file` → `CURL_UNSUPPORTED` |
| `-F`, `--form`, `--form-string`, `--data-urlencode` | body mà v1 không chạy được: `bodyKind = unsupported`, kèm cảnh báo |
| `--url` hoặc một từ không phải flag | URL; URL thứ hai → `CURL_PARSE_ERROR` |
| `-u`, `--user` | `Authorization: Basic base64(user:password)`; không có `:` thì password rỗng, kèm cảnh báo |
| `--oauth2-bearer` | `Authorization: Bearer <token>` |
| `-b`, `--cookie` | header `Cookie` khi giá trị có `=`; ngược lại đó là file cookie và bị bỏ qua kèm cảnh báo |
| `-A`, `--user-agent` | header `User-Agent` |
| `-e`, `--referer` | header `Referer` (bỏ hậu tố `;auto`) |
| `-k`, `--insecure` | `insecure = true`; có được áp dụng hay không là quyết định chính sách (§13) |
| `-I`, `--head` | method `HEAD` khi không có `-X` |
| `-G`, `--get`, `-T`, `--upload-file`, `--request-target`, `--aws-sigv4` | `CURL_UNSUPPORTED`: nếu bỏ qua thì tool sẽ gửi một request khác với curl |
| `-L`, `--location` | bỏ qua kèm cảnh báo *"redirects are never followed, a 3xx is reported as the result"* (§11.2) |
| `-m`, `--max-time`, `--connect-timeout` | bỏ qua: dùng timeout của run |
| `--retry` | bỏ qua: API Case Runner không bao giờ retry |
| `-x`, `--proxy`, `--resolve`, `--connect-to` | bỏ qua: request đi thẳng tới host của URL |
| `--compressed`, `-s`, `-S`, `-v`, `-i`, `-f`, `-g`, `-N`, `--http1.1`, `--http2`, `-o`, `-w`, `--cacert`, `--cert`, … (flag về output, file TLS và transport) | bỏ qua kèm cảnh báo *"Ignored <flag>"*; flag đã biết là nhận giá trị thì ăn luôn giá trị đó |
| Flag lạ khác | bỏ qua kèm cảnh báo *"Ignored unknown flag <flag>"*; coi như không nhận giá trị |

### 6.4 Dựng template

- **Method**: dùng `-X` nếu có; không thì `HEAD` khi có `-I`; không thì `POST` khi có body; còn lại là `GET`.
- **URL**: URL không có `://` được thêm `http://` như curl, kèm cảnh báo. Chỉ nhận `http` và `https` (khác thì `CURL_UNSUPPORTED`); URL không có host → `CURL_PARSE_ERROR`.
- **Body**: các phần body nối với nhau bằng `&` theo thứ tự, như curl, kèm cảnh báo khi có nhiều hơn một phần.
- **`bodyKind`**: `none` (không có body), `json` (body là JSON hợp lệ), `unsupported` (body khác, hoặc dùng flag form). Với `unsupported`, FE hiện *"v1 supports JSON bodies only"* và request không chạy được.
- Body JSON mà không có header `Content-Type` sẽ có cảnh báo: API có thể không đọc nó như JSON (bản thân curl sẽ gửi `application/x-www-form-urlencoded`).

### 6.5 Lỗi

Lệnh bị từ chối trả về `ParseError` gồm mã lỗi và vị trí **ký tự** tính từ 1 (không phải byte, nên chữ có dấu vẫn chỉ đúng chỗ); message kết thúc bằng *"at position N"* khi có vị trí.

| Mã | Khi nào | Ví dụ message |
|---|---|---|
| `CURL_PARSE_ERROR` | chuỗi rỗng; từ đầu không phải `curl`; quote chưa đóng; flag thiếu giá trị; không có URL; hai URL; URL sai hoặc không có host | *"Missing closing ' for the quote opened at position 9"* |
| `CURL_UNSUPPORTED` | curl hợp lệ nhưng v1 không tái tạo được: body hoặc header đọc từ file, `-G`, `-T`, `--request-target`, `--aws-sigv4`, scheme không phải http(s), body JSON có key trùng (§7) | *"-d @body.json reads the body from a file, which is not supported; paste the body itself at position 16"* |

## 7. Field Extractor (làm phẳng JSON)

### 7.1 Quy tắc

- Chỉ liệt kê **leaf** (string, number, boolean, null). Object/array rỗng cũng coi là leaf (type `object`/`array`) để tester biết nó tồn tại.
- Path: object dùng `.`, mảng dùng `[i]`. Ví dụ `data.account.id`, `items[0].sku`.
- Key rỗng hoặc chứa `.`, `[`, `]`, `"` hay `\` được viết thành đoạn ngoặc vuông có quote JSON: `["key.with.dot"]`, `x[""]`. Các key khác, kể cả có khoảng trắng hay dấu tiếng Việt, dùng dạng chấm.
- Giữ **thứ tự key** như body gốc (không decode vào `map`; đọc bằng `json.Decoder.Token()` hoặc dùng thư viện giữ thứ tự).
- Number: giữ nguyên dạng chữ (`json.Number`); **không** chuyển sang float64 (số tiền và số tài khoản dài sẽ mất chính xác).
- `sampleValue` được ghi theo đúng cách tester gõ vào ô, để một dòng toàn giá trị mẫu dựng lại đúng body gốc: chuỗi rỗng là `<EMPTY>`, `null` là `<NULL>`, object/array rỗng là `{}`/`[]`.
- Cho phép mảng ở cấp gốc (`[0].id`). Body cấp gốc là giá trị đơn hoặc rỗng thì không có field; khi đó response parse có cảnh báo *"The JSON body has no fields to vary"*.
- Body lặp key trong cùng một object bị từ chối với `CURL_UNSUPPORTED` (một path sẽ trỏ tới hai giá trị). Lồng sâu quá 512 tầng cũng bị từ chối như vậy.

### 7.2 Ví dụ

Body:
```json
{
  "requestId": "REQ001",
  "data": {
    "amount": 100000,
    "account": {"id": "0123456789", "type": "SAVING"},
    "note": "test",
    "urgent": false
  },
  "items": [{"sku": "A1", "qty": 2}]
}
```

Output:
| path | type | sampleValue |
|---|---|---|
| `requestId` | string | `REQ001` |
| `data.amount` | number | `100000` |
| `data.account.id` | string | `0123456789` |
| `data.account.type` | string | `SAVING` |
| `data.note` | string | `test` |
| `data.urgent` | boolean | `false` |
| `items[0].sku` | string | `A1` |
| `items[0].qty` | number | `2` |

## 8. Bảng test case (UI)

Không có file test data để sinh hay import. Ngay khi curl được phân tích (§6, §7), **cấu hình hiện ngay dưới ô curl** trên cùng trang: field rules, rồi tới bảng test case chỉnh sửa được. Tester bấm **`+`** để thêm dòng và điền mỗi dòng một case.

### 8.1 Cột

Bảng được dựng từ các field đã phân tích; các cột cố định từ lúc Analyze:

| Cột | Nội dung | Ô trống |
|---|---|---|
| `#` | Số case `1.`, `2.`, `3.` …, tự đánh theo thứ tự dòng và đánh lại khi xoá hay đổi thứ tự dòng. Không sửa được. | — |
| `name` | Tên case, nhập tự do | `Case <n>` |
| mỗi field path một cột (§7), theo thứ tự body; tiêu đề cột hiện path, kiểu và tag Required/Unrequired | Giá trị sẽ gửi. Quy tắc ô như §9: `<EMPTY>` → `""`, `<NULL>` → `null` | không nhập: Required → BLOCKED, Unrequired → xoá key |
| `expect` | Mã phải xuất hiện ở đâu đó trong response (D14), ví dụ `00`, `ERR_AMOUNT_INVALID`, `401` | không được để trống: case bị BLOCKED |
| thao tác | Nhân bản dòng, xoá dòng | — |

Ví dụ, với body ở §7.2 và `data.note` đặt là Unrequired:

| # | name | requestId | data.amount | data.account.id | … | data.note | … | expect |
|---|---|---|---|---|---|---|---|---|
| 1. | Valid transfer | REQ001 | 100000 | 0123456789 | … | test | … | `"code":"00"` |
| 2. | Amount is zero | REQ002 | 0 | 0123456789 | … | test | … | `ERR_AMOUNT_INVALID` |
| 3. | Note omitted | REQ003 | 50000 | 0123456789 | … | | … | `"code":"00"` |
| 4. | Account id missing | REQ004 | 50000 | | … | test | … | `ERR_ACCOUNT_REQUIRED` |
| **`+`** | | | | | | | | |

Case 1 và 3 dùng expect `"code":"00"` thay vì `00`, để mã thành công không khớp nhầm vào số tiền như `100000` (D14). Case 3 không gửi key `data.note` (Unrequired, để trống). Case 4 bị **BLOCKED** và không bắn, vì `data.account.id` là Required, dù mã expect của nó là mã lỗi; muốn thử API tự validate việc thiếu account id thì tester đổi field đó sang Unrequired trước (ghi chú ở §9).

### 8.2 Hành vi

- **`+`** thêm một dòng mới **điền sẵn giá trị mẫu của curl** và ô `expect` trống để tester điền, để case mới bắt đầu từ một request chạy được và tester chỉ sửa đúng chỗ case muốn thử. Sau khi Analyze, bảng có sẵn một dòng như vậy.
- **Nhân bản** chép một dòng xuống ngay dưới nó; **xoá** bỏ dòng đó. Cả hai đều đánh lại `#`.
- Ô là text input thường; gõ được `<EMPTY>` và `<NULL>` như vậy.
- Đổi rule của field (Required ↔ Unrequired) cập nhật tag ở tiêu đề cột và phần kiểm tra trước ngay lập tức; giá trị đã nhập được giữ nguyên.
- Analyze một curl **khác** sẽ dựng lại các cột. Giá trị được giữ cho các field path vẫn còn; nếu có dòng sẽ mất dữ liệu thì hỏi tester xác nhận trước.
- Nút `+` bị khoá khi đủ `CASERUNNER_MAX_CASES` dòng (mặc định 1000); BE cũng áp dụng giới hạn này (§13).

## 9. Validator

Chạy ở BE cho **từng case** trước khi bắn. Một case có thể có **nhiều lỗi**; gom hết lại rồi báo một lần.

Quy ước giá trị ô do tester nhập (luôn là chuỗi):
- `""` (trống) = **không nhập**.
- `<EMPTY>` = gửi chuỗi rỗng `""` (theo OD4).
- `<NULL>` = gửi `null` (theo OD4).
- Còn lại = giá trị cần ép về kiểu của field.

| Điều kiện | Kết quả |
|---|---|
| Field **Required** + ô trống | lỗi `REQUIRED_MISSING`: *"Field `data.amount` is Required. Enter a value or change it to Unrequired."* |
| Field **Unrequired** + ô trống | hợp lệ; field sẽ bị **xoá** khỏi request |
| type `number` mà giá trị không phải số hợp lệ | lỗi `TYPE_MISMATCH`: *"Field `data.amount` expects type number, got 'abc'"* |
| type `boolean` mà không phải `true`/`false` | lỗi `TYPE_MISMATCH` |
| type `string` | luôn hợp lệ |
| `<NULL>` | hợp lệ với mọi type (tester cố ý thử null) |
| type `object` / `array` | ô phải là JSON đúng kiểu đó (`{"a":1}`, `[1,2]`); ngược lại `TYPE_MISMATCH` |
| type `null` (curl gửi `null`) | mọi giá trị JSON; chữ khác được gửi dạng chuỗi |
| request dựng ra dùng `{{name}}` mà không bước lấy token nào bắt | lỗi `UNKNOWN_VARIABLE`: *"Unknown variable {{otp}}: no token step captures it"* |
| `expect` để trống (D15) | lỗi `INVALID_EXPECTATION`: *"Case needs an expect code"* |

Có lỗi → case thành **BLOCKED**, ghi `errors[]`, và **không bắn**.

> Ghi chú: muốn thử API có validate "thiếu field" không thì tester đổi field đó sang **Unrequired** rồi để trống. Request sẽ không có field đó; đặt `expect` là mã lỗi API phải trả về.

## 10. Request Builder

Với mỗi case hợp lệ:

1. **Deep clone** body template (template dùng chung giữa các goroutine không bao giờ được sửa).
2. Với mỗi field:
   - có giá trị → set vào path, đúng kiểu (`number` ghi dạng số JSON, không bọc quote).
   - Unrequired + trống → **xoá key** khỏi object cha.
     - Nếu path nằm trong mảng (`items[0].sku`) → xoá key `sku` trong phần tử đó, **không** xoá phần tử mảng.
     - Object cha trở thành rỗng → giữ `{}` (không xoá dây chuyền lên trên).
3. Serialize lại JSON, giữ thứ tự key gốc.
4. Method, URL, headers giữ nguyên như curl. `Content-Length` được tính lại (HTTP client tự làm; không copy header `Content-Length` từ curl).

Lưu `requestBody` đã dựng vào kết quả để tester đối chiếu trong báo cáo.

## 11. Runner (worker pool)

### 11.1 Mô hình (Go)

```
POST /api/runs
   ↓
create Run{status: RUNNING}, save to RunStore, return 202 {runId}
   ↓
go runner.Execute(ctx, run)        // ctx is tied to the run, not to the HTTP request
   ↓
sem := make(chan struct{}, concurrency)
for each valid case:
    sem <- struct{}{}               // blocks while N goroutines are running
    go func(c) {
        defer func(){ <-sem }()
        defer recover()             // a panic in one case must not crash the whole run
        reqCtx, cancel := context.WithTimeout(ctx, timeout)
        defer cancel()
        result := send(reqCtx, c)
        result = classify(result)
        run.Save(result)            // mutex-protected
        broker.Publish(runId, result)
    }(c)
wait for all → run.status = DONE → publish "done"
```

Có thể dùng `golang.org/x/sync/errgroup` với `SetLimit(n)` thay cho semaphore tự viết, nhưng **không** để lỗi của một case huỷ các case khác (lỗi của case là dữ liệu kết quả, không phải lỗi của group).

### 11.2 Quy tắc bắt buộc

- **Không retry.** API payment/transfer có thể đã commit dù client timeout. Retry có thể tạo giao dịch trùng. Timeout ghi nhận là `EXCEPTION` với `errorType = TIMEOUT`, kèm ghi chú *"Cannot determine whether the server processed the request"*.
- Dùng **một** `http.Client` chung cho cả app (connection pool); không tạo client mới mỗi request. `CheckRedirect` trả `http.ErrUseLastResponse` (không tự follow redirect, để tester thấy 3xx).
- Đọc response body tối đa **1 MB** (`io.LimitReader`); phần dư cắt bỏ và đánh dấu `truncated=true`.
- Luôn `resp.Body.Close()`.
- Đo `durationMs` từ lúc gửi tới lúc đọc xong body.
- Thứ tự hoàn thành **không** theo thứ tự case. Mỗi kết quả mang `caseIndex` để FE và báo cáo sắp xếp lại.
- Hỗ trợ **huỷ run**: `POST /api/runs/{id}/cancel` → huỷ `ctx` của run. Case chưa chạy → `CANCELLED`; case đang chạy → `EXCEPTION` (`errorType = CANCELLED`).
- **Vệ sinh request**: không gửi header `Content-Length` và `Accept-Encoding` của curl (client tự đặt độ dài và tự thoả thuận nén, nên body gzip copy từ DevTools vẫn đọc được thành chữ); header `Host` đặt host của request.

### 11.3 Bước chuẩn bị (luồng token tuỳ chọn, D20–D21)

Một bước chuẩn bị gồm một curl (parse như curl chính, §6; chấp nhận mọi loại body, nên request lấy token OAuth dạng form vẫn chạy được) và danh sách **capture** `{var, path}`.

1. Các bước chạy theo thứ tự. Trước khi gửi một bước, placeholder `{{name}}` trong URL, giá trị header và body được thay bằng các biến đã bắt được tới lúc đó; trong body JSON giá trị được escape kiểu JSON. Biến chưa có làm bước đó lỗi.
2. Một bước thành công khi status của response là 2xx **và** mọi capture đều tìm được giá trị. Ngược lại bước lỗi kèm lý do (*"Expected a 2xx response, got HTTP 401"*, *"token: no value at data.accessToken"*), và các bước sau bị bỏ qua.
3. Capture có **path** (cú pháp §7, ví dụ `data.accessToken`) đọc giá trị đó từ response JSON. Capture **không có path** tự tìm token: giá trị chuỗi khác rỗng đầu tiên có key là, theo thứ tự ưu tiên, `access_token`, `accessToken`, `token`, `id_token`, `idToken`, `jwt`, `auth_token`, `authToken`, `session_token`, `sessionToken` (không phân biệt hoa thường, ở mọi tầng). Capture đầu tiên của bước đầu tiên mặc định tên là `token`.
4. Trước khi gửi một case, request chính cũng được thay biến như vậy. Khi **Inject token** bật (mặc định), header `Authorization` của request chính được đặt thành `Bearer {{token}}` (thay header `Authorization` có sẵn trong curl, hoặc thêm vào nếu chưa có); khi có bước lấy token và Inject token bật mà không bước nào bắt biến tên `token`, run bị từ chối với `400` *"Inject token needs a capture named token"*.
5. Trong một run (D21), các bước chạy trước mỗi case; nếu lỗi thì case đó là `EXCEPTION` với `errorType = PREPARE_FAILED` kèm lý do của bước lỗi, và run tiếp tục với case kế.
6. Giá trị bắt được là bí mật: không bao giờ ghi log và được che trên màn hình như `Authorization` (§13).

`POST /api/prepare/try` (§15.7) chạy các bước một lần để tester kiểm tra giá trị bắt được trước khi chạy case.

## 12. Result Classifier

Mỗi case đã bắn chỉ được chấm theo **mã expect** (D14): bằng đúng HTTP status code, hoặc nằm trong body đã đọc (tối đa 1 MB, §11.2), hoặc trong một header của response (`Name: value`) không thuộc nhóm header kỹ thuật nêu ở D14:

| Status | Điều kiện |
|---|---|
| `BLOCKED` | Validator báo lỗi; case không được bắn |
| `EXCEPTION` | Không nhận được HTTP response hợp lệ (timeout, connection refused, lỗi DNS, lỗi TLS, response hỏng, bị huỷ), hoặc một bước chuẩn bị bị lỗi (`PREPARE_FAILED`) |
| `SUCCESS` | Mã expect là status code, hoặc xuất hiện trong body hay một header của ứng dụng |
| `FAILED` | Không xuất hiện |
| `CANCELLED` | Run bị huỷ trước khi case được bắn |

Thứ tự kiểm tra: BLOCKED → EXCEPTION → tìm mã expect. Thứ tự tìm là status → body → header, và kết quả ghi lại nơi tìm thấy mã (`status`, `body` hoặc `header`).

Mỗi kết quả có `reason` dễ đọc cho tester, ví dụ:
- `Found ERR_AMOUNT_INVALID in the body (HTTP 400)`
- `00 not found in the response (HTTP 500)` (mã được hiển thị đúng như đã gõ: `Found "code":"00" in the body (HTTP 200)`)
- `"Prepare step 1 failed: Expected a 2xx response, got HTTP 401"`
- `"Timed out after 30s. Cannot determine whether the server processed the request"`
- `"Could not connect to uat-api.example.com:443 (connection refused)"`

`errorType` cho EXCEPTION: `TIMEOUT` | `CONNECTION` | `DNS` | `TLS` | `INVALID_RESPONSE` | `CANCELLED` | `PREPARE_FAILED` | `POLICY` | `INTERNAL`.

## 13. An toàn & bảo mật

Tool này gửi request tới URL tuỳ ý theo input, nên phải có rào chắn:

1. **Allowlist host**: env `CASERUNNER_ALLOWED_HOSTS` (ví dụ `localhost,*.uat.example.com,10.10.*`; `*` khớp mọi ký tự, không phân biệt hoa thường, bỏ qua cổng; pattern chỉ gồm chữ số, dấu chấm, dấu hai chấm và `*`, như `10.10.*`, chỉ khớp địa chỉ IP, không bao giờ khớp domain như `10.10.attacker.example`). Áp dụng cho mọi request gửi đi: bước chuẩn bị và case. Host không khớp thì request đó lỗi với `errorType = POLICY` và *"Host x is not in CASERUNNER_ALLOWED_HOSTS"*. Rỗng = cho phép tất cả, và ghi log cảnh báo lúc khởi động.
2. **Giới hạn**: concurrency tối đa, số case tối đa, timeout tối đa (OD4). BE luôn kẹp (clamp) giá trị FE gửi lên.
3. **`-k/--insecure`**: chỉ bỏ verify TLS khi env `CASERUNNER_ALLOW_INSECURE=true`. Ngược lại request lỗi với `errorType = POLICY` và thông báo rõ ràng. Mặc định dùng system trust store. Môi trường công ty có CA nội bộ thì cài CA vào trust store, không tắt verify.
4. **Che giá trị nhạy cảm**: trong log server và **trong báo cáo xuất ra**, che giá trị header `Authorization`, `Cookie`, `X-Api-Key` và header có chứa `token`/`secret`, chỉ giữ 6 ký tự đầu + `***`. UI kết quả cũng che mặc định.
5. **Không log body** request/response ở level INFO (có thể chứa dữ liệu khách hàng). Chỉ log `runId`, `caseIndex`, status, duration.
6. Mặc định server chỉ bind `127.0.0.1`. Muốn cho cả team dùng thì cấu hình `CASERUNNER_BIND`.
7. **Kích thước request**: body của `POST /api/parse` lớn hơn 2 MB bị từ chối với `413 REQUEST_TOO_LARGE`. Access log chỉ ghi method, path, status và thời gian, không bao giờ ghi header hay body.
8. **Tấn công qua trình duyệt vào server local**: một trang web khác đang mở trong trình duyệt của tester không được điều khiển tool. Mọi request đi qua một lớp guard: lời gọi `/api/` thay đổi trạng thái (`POST`) phải là `application/json` (nên trình duyệt buộc phải gửi CORS preflight, mà server không bao giờ cho phép) và bị từ chối với `403 FORBIDDEN` khi `Origin` hoặc `Sec-Fetch-Site` cho thấy nó đến từ trang khác; khi bind vào loopback, header `Host` khác `127.0.0.1`, `localhost` hoặc `[::1]` kèm đúng cổng bị từ chối với `403` (DNS rebinding). Bind ra mạng (`CASERUNNER_BIND=0.0.0.0:…`) bỏ qua kiểm tra `Host` và ghi log cảnh báo: ai vào được cổng đó cũng dùng được tool, điều này được chấp nhận khi dùng trong mạng công ty.

## 14. Cấu trúc thư mục

### 14.1 Backend: Clean Architecture (D18)

Phụ thuộc chỉ hướng vào trong: `adapter` → `usecase` → `domain`. `cmd/caserunner/main.go` là composition root và là nơi duy nhất biết mọi tầng.

| Tầng | Chứa | Được import |
|---|---|---|
| `domain` | Entity và business rule thuần: parse curl, làm phẳng field, validate, dựng request, phân loại kết quả. Không I/O, không goroutine, không clock, không `net/http`. | chỉ thư viện chuẩn |
| `usecase` | Application rule: mỗi use case một file (parse curl, start/get/cancel/watch run, xuất báo cáo), worker pool (§11), allowlist host và các giới hạn (§13). Khai báo các **port** (interface) nó cần. | `domain` |
| `adapter` | Phần cài đặt các port và HTTP API đầu vào: handler + SSE, HTTP sender gửi đi, run store in-memory, event broker, bộ dựng báo cáo. | `usecase`, `domain`, thư viện ngoài |
| `config` | Env → `Config` (§20). | chỉ thư viện chuẩn |

Port là các interface nhỏ khai báo trong `usecase/ports.go`, cạnh code dùng chúng (đúng thói quen Go): `RunRepository`, `RequestSender`, `EventPublisher`, `ReportRenderer`, `Clock`, `IDGenerator`. Không khai báo interface cho thứ chỉ có một cài đặt mà test không cần thay.

## 15. API & mô hình dữ liệu

### 15.1 Endpoint

| Method | Path | Mô tả |
|---|---|---|
| `POST` | `/api/parse` | Parse curl → request template + danh sách field |
| `POST` | `/api/prepare/try` | Chạy các bước chuẩn bị một lần và trả về giá trị mỗi bước bắt được (§15.7) |
| `POST` | `/api/runs` | Tạo run và bắt đầu bắn. Trả `202 {runId}` |
| `GET` | `/api/runs/{runId}` | Snapshot hiện tại (dùng khi SSE rớt kết nối) |
| `GET` | `/api/runs/{runId}/events` | SSE stream |
| `POST` | `/api/runs/{runId}/cancel` | Huỷ run |
| `GET` | `/api/runs/{runId}/export?format=xlsx\|pdf` | Tải báo cáo |
| `GET` | `/api/health` | Health check |

Các path ngoài `/api/` phục vụ FE đã nhúng (D19); path không tồn tại ở đó trả về `index.html` của app.

Định dạng lỗi chung:
```json
{ "error": { "code": "CURL_PARSE_ERROR", "message": "Missing closing ' for the quote opened at position 57" } }
```

| Mã | HTTP | Khi nào |
|---|---|---|
| `BAD_REQUEST` | 400 | Body của request không phải JSON hợp lệ |
| `CURL_PARSE_ERROR` | 400 | Chuỗi curl không phải lệnh dùng được (§6.5) |
| `CURL_UNSUPPORTED` | 400 | Curl hợp lệ nhưng v1 không chạy được (§6.5) |
| `FORBIDDEN` | 403 | Request đến từ trang khác, hoặc `Host` không được chấp nhận (§13 mục 8) |
| `NOT_FOUND` | 404 | Không có API endpoint ở path đó |
| `RUN_NOT_FOUND` | 404 | Run không tồn tại hoặc đã hết hạn: *"Run has expired, please run it again"* |
| `METHOD_NOT_ALLOWED` | 405 | Path tồn tại nhưng với method khác; header `Allow` liệt kê các method đó |
| `REQUEST_TOO_LARGE` | 413 | Body của request vượt giới hạn (§13) |
| `TOO_MANY_RUNS` | 429 | Cả `CASERUNNER_MAX_RUNS` run đều đang chạy (§15.6) |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | `POST` tới `/api/` mà không phải `application/json` (§13 mục 8) |
| `INTERNAL` | 500 | Lỗi server ngoài dự kiến, kể cả panic đã được bắt |

### 15.2 `POST /api/parse`

Request:
```json
{ "curl": "curl -X POST 'https://...' -H 'Content-Type: application/json' -d '{...}'" }
```
Response 200:
```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json", "insecure": false },
  "fields": [
    { "path": "data.amount", "type": "number", "sampleValue": "100000" }
  ],
  "warnings": []
}
```

- `headers`, `fields` và `warnings` luôn là mảng, không bao giờ là `null`.
- `fields` rỗng trừ khi `bodyKind` là `json`.
- Giá trị header được trả về nguyên bản, không che, vì FE gửi lại template trong `POST /api/runs`; FE tự che trên màn hình (§16).
- `type` là một trong `string`, `number`, `boolean`, `null`, `object`, `array`.

### 15.3 `POST /api/runs`

BE không giữ trạng thái giữa parse và run: FE gửi lại toàn bộ template (BE không cần nhớ kết quả parse).

```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json" },
  "fields": [
    { "path": "data.amount",     "type": "number", "rule": "REQUIRED" },
    { "path": "data.note",       "type": "string", "rule": "UNREQUIRED" }
  ],
  "cases": [
    {
      "no": 1,
      "name": "Valid transfer",
      "values": { "data.amount": "50000", "data.note": "" },
      "expect": "\"code\":\"00\""
    }
  ],
  "prepare": {
    "steps": [ { "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json" }, "captures": [ { "var": "token", "path": "" } ] } ],
    "injectToken": true
  },
  "options": { "concurrency": 5, "timeoutMs": 30000 }
}
```
`prepare` là tuỳ chọn; khi có bước, `concurrency` bị bỏ qua và các case chạy lần lượt (D21).

Response `202`:
```json
{ "runId": "r_8f3a...", "total": 1, "blocked": 0 }
```

### 15.4 Mô hình kết quả

```go
type CaseStatus string // SUCCESS | FAILED | EXCEPTION | BLOCKED | CANCELLED | PENDING | RUNNING

type CaseResult struct {
    CaseIndex      int               `json:"caseIndex"`
    CaseNo         int               `json:"caseNo"`                   // the # shown in the case table (§8.1)
    Name           string            `json:"name"`
    Status         CaseStatus        `json:"status"`
    Reason         string            `json:"reason"`
    Errors         []ValidationError `json:"errors,omitempty"`     // when BLOCKED
    ErrorType      string            `json:"errorType,omitempty"`  // when EXCEPTION
    Input          map[string]string `json:"input"`
    RequestBody    string            `json:"requestBody,omitempty"`
    Expect         string            `json:"expect"`
    FoundIn        string            `json:"foundIn,omitempty"`        // status | header | body; empty when not found
    HTTPStatus     int               `json:"httpStatus,omitempty"`
    ResponseBody   string            `json:"responseBody,omitempty"`
    Truncated      bool              `json:"truncated,omitempty"`
    StartedAt      time.Time         `json:"startedAt"`
    DurationMs     int64             `json:"durationMs"`
}

type ValidationError struct {
    Field   string `json:"field"`
    Code    string `json:"code"`    // REQUIRED_MISSING | TYPE_MISMATCH | INVALID_EXPECTATION | UNKNOWN_VARIABLE
    Message string `json:"message"`
}

type Run struct {
    ID        string
    Status    string        // RUNNING | DONE | CANCELLED
    CreatedAt time.Time
    Template  RequestTemplate
    Fields    []FieldRule
    Results   []CaseResult  // index = caseIndex
    Summary   Summary       // counts by status
    mu        sync.Mutex
    cancel    context.CancelFunc
}
```

### 15.5 SSE event

```
event: snapshot      # sent immediately on connect: the full current state
data: {"runId":"...","status":"RUNNING","results":[...],"summary":{...}}

event: case          # whenever a case has a result
data: {CaseResult}

event: done
data: {"runId":"...","status":"DONE","summary":{"total":10,"success":6,"failed":2,"exception":1,"blocked":1,"cancelled":0}}
```

- Gửi `snapshot` đầu tiên giúp client kết nối muộn hoặc kết nối lại không mất dữ liệu. Không cần `Last-Event-ID`.
- Gửi comment heartbeat `: ping` mỗi 15s để proxy (Nginx) không cắt kết nối. Header: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
- Publish không được chặn worker: mỗi subscriber có channel có buffer; đầy thì bỏ subscriber đó (client sẽ kết nối lại và nhận snapshot).

### 15.6 RunStore

- `map[string]*Run` + `sync.RWMutex`.
- TTL mặc định **1 giờ** sau khi run kết thúc (`CASERUNNER_RUN_TTL`). Một goroutine janitor dọn mỗi phút.
- Tối đa **50 run** trong bộ nhớ. Vượt thì xoá run DONE cũ nhất. Nếu tất cả đang RUNNING → `429 TOO_MANY_RUNS`.
- Run hết hạn → `GET` / `events` / `cancel` / `export` trả `404 RUN_NOT_FOUND` *"Run has expired, please run it again"*.

### 15.7 `POST /api/prepare/try`

Chạy các bước chuẩn bị một lần, theo thứ tự, với chính sách ở §13 (allowlist, `-k`, timeout bị kẹp theo `CASERUNNER_MAX_TIMEOUT_MS`).

Request:
```json
{
  "steps": [
    { "template": { "method": "POST", "url": "https://uat-api.example.com/auth/login", "headers": [...], "bodyRaw": "...", "bodyKind": "json", "insecure": false },
      "captures": [ { "var": "token", "path": "" } ] }
  ],
  "options": { "timeoutMs": 30000 }
}
```
Response 200 (kể cả khi một bước lỗi; lỗi nằm trong bước đó):
```json
{
  "steps": [
    { "status": "OK", "httpStatus": 200, "durationMs": 182, "reason": "",
      "captured": [ { "var": "token", "path": "data.accessToken", "value": "eyJ..." } ],
      "responseBody": "{...}", "truncated": false }
  ],
  "vars": { "token": "eyJ..." }
}
```
- `status`: `OK`, `FAILED` (kèm `reason`, và `errorType` khi không nhận được response), hoặc `SKIPPED` (một bước trước đã lỗi).
- `path` là path đã đọc ra giá trị, cho biết việc tự tìm token đã thấy nó ở đâu.
- Tối đa 10 bước mỗi request; body của request giới hạn 2 MB như `/api/parse`.

## 16. FE (React + TS + Vite + Ant Design)

**Một trang duy nhất** chia hai cột: **Cấu hình** bên trái (bước 0–3 là các phần gập/mở, khi gập hiện một dòng tóm tắt; Nhập/Xuất cấu hình ở đầu cột), **Test case** và **Kết quả** bên phải, nên curl luôn trong tầm tay khi nhập case. Dưới 1200 px hai cột xếp chồng. Toàn bộ state giữ trong React (`useReducer` hoặc Zustand; không cần Redux).

**Thanh trên** (cố định). Tiêu đề, nút **Chạy** (thành **Huỷ run** khi đang chạy, **Chạy lại** sau đó), số case theo từng trạng thái đã xong, tag sức khoẻ backend (`BE OK · <version>`, hoặc `BE down` kèm banner lỗi) và nút đổi ngôn ngữ **VI / EN** (D22).

**0. Phần Bước chuẩn bị** (tuỳ chọn, ẩn cho tới khi tester bấm **Add token step**): mỗi bước một thẻ có ô curl và nút Analyze riêng, bảng capture (tên biến, path; path trống nghĩa là tự tìm token), và nút xoá. **Try steps** chạy các bước (§15.7) và hiện dưới mỗi bước: trạng thái, mã HTTP, lý do, giá trị bắt được (bị che cho tới khi bật **Show sensitive values**) và response body. Công tắc **Inject token** (mặc định bật) quyết định có đặt `Authorization: Bearer {{token}}` cho request chính hay không.

**1. Phần Curl**. `Input.TextArea` (font monospace, cao theo nội dung) + nút **Analyze**; **Ctrl/⌘+Enter** cũng phân tích. Lỗi parse hiện bên dưới dạng *"Cannot use this curl"* kèm message của backend.

**2. Phần Request** (hiện sau khi Analyze):
- Tag method + URL (copy được), tag `-k / --insecure` khi có, và loại body (`JSON`, `No body`, `Unsupported`).
- Banner lỗi *"v1 supports JSON bodies only"* khi loại body là `unsupported`.
- Danh sách cảnh báo của parser.
- Bảng header; giá trị nhạy cảm bị che (§13) cho tới khi tester bật **Show sensitive values**. Khi có bước chuẩn bị và **Inject token** bật, dòng `Authorization` ghi rõ sẽ bị thay.
- Liệt kê các placeholder `{{name}}` tìm thấy trong curl chính; placeholder nào không có bước chuẩn bị nào bắt thì được đánh dấu.

**3. Phần Field rules** (chỉ khi body là JSON):
- `Table` gồm Field path | Type (tag màu) | Sample value | Rule (`Select` Required/Unrequired, mặc định Required), kèm nút **All Required** / **All Unrequired** và số đếm mỗi loại rule.
- Analyze lại thì mỗi field path còn tồn tại giữ nguyên rule cũ; path mới bắt đầu là Required.

**4. Phần Test case** (cột phải, chỉ khi body là JSON):
- **Bảng case** (§8): sau khi Analyze có sẵn một dòng điền mẫu, **`+ Thêm case`** để thêm, Nhân bản / Xoá từng dòng; ô `expect` bắt buộc; phân trang 50 dòng.
- Kiểm tra trước ở FE: ô Required hoặc expect trống được tô đỏ kèm tooltip (D4, D15), và một dòng đếm số case sẽ bị chặn. Vẫn cho chạy, sau khi xác nhận *"X case sẽ bị chặn"*.
- Tuỳ chọn run: số request song song (1–20; cố định 1 khi có bước lấy token, D21), timeout (1–120 giây).
- Nút **Chạy** nằm trên thanh trên. **Export config** lưu `{version:1, prepare, curl, rules, cases, options}` (không bao giờ lưu giá trị đã bắt); **Import config** nạp lại và Analyze lại các curl.

**5. Phần Kết quả** (dưới bảng case; trống cho tới lần chạy đầu):
- Thanh `Progress` (đã xong / tổng) và bộ lọc trạng thái kèm số đếm (SUCCESS xanh lá / FAILED đỏ / EXCEPTION cam / BLOCKED / CANCELLED); kết quả về dần từng case qua SSE.
- `Table` sắp theo số case: #, Tên, Expect, HTTP, Trạng thái (`Tag` màu), Thời gian, Lý do; có bộ lọc theo trạng thái. Bấm một dòng mở `Drawer` với trạng thái, lý do, nơi tìm thấy mã, các giá trị đã gửi, request body và response body có tô sáng mã expect.
- **Huỷ run** khi đang chạy, **Chạy lại** sau đó, cả hai trên thanh trên (giữ cấu hình; thay kết quả cũ).
- Ghi chú cố định: kết quả chỉ được giữ trong bộ nhớ một thời gian (mặc định 1 giờ) và mất khi tool khởi động lại. Xuất Excel/PDF có ở Step 10.

## 19. Kiểm thử

- **Unit**: các package `domain` (curl, field, testcase, run classifier). Đây là nơi chứa business rule, cần test kỹ nhất.
- **Use case**: `usecase` với fake in-memory của các port (worker pool, huỷ, giới hạn).
- **Integration**: `adapter/sender` + `httptest.Server`; handler của `adapter/httpapi` với `httptest.NewRecorder`.
- **Race**: luôn chạy `go test -race ./...` (worker pool, memstore, broker).
- **E2E thủ công**: FE + BE + mockapi, 50 case, concurrency 5, có vài case BLOCKED/timeout.

Các case quan trọng không được bỏ sót:
1. Field Required bỏ trống → BLOCKED, và **không** có request nào tới server giả (đếm số hit).
2. Field Unrequired bỏ trống → request **không chứa** key đó.
3. Số lớn / số tiền giữ đủ độ chính xác trong request gửi đi.
4. Timeout → EXCEPTION/TIMEOUT, **không** retry (server giả chỉ nhận đúng 1 hit).
5. Số request đồng thời không bao giờ vượt `concurrency`.
6. Panic trong một case không làm sập run.
7. Huỷ run giữa chừng → case chưa chạy là CANCELLED.
8. Expect là tìm chuỗi con trong status, header và body: `ERR_X` trong body → SUCCESS bất kể HTTP status; `401` là status → SUCCESS; không có mã → FAILED.
10. Có bước chuẩn bị thì mỗi case nhận một token mới bắt được (`/secure` thấy token khác nhau ở mỗi case), và login lỗi chỉ làm case đó thành `PREPARE_FAILED`.
9. Một dòng thêm bằng `+` mà không sửa gì thì tạo ra request giống hệt body gốc của curl.

## 21. Build và chạy

`caserunner/scripts/build.sh` build FE (`npm ci` ở lần đầu, sau đó `npm run build`), chép `frontend/dist` vào `backend/internal/adapter/web/dist`, rồi build `backend/bin/caserunner` với version lấy từ `VERSION` (mặc định `dev`). Chạy binary đó là có cả giao diện lẫn API ở `http://127.0.0.1:8080` (`CASERUNNER_BIND`). `--run` chạy nó ngay sau khi build; API Case Runner nào đang lắng nghe ở cổng đó sẽ bị tắt trước (Ctrl+C, quá 10 giây thì buộc tắt), còn chương trình khác ở cổng đó làm build dừng lại mà không bị động tới. `scripts/build.ps1` (kèm `-Run`) làm điều tương tự trên Windows và ghi ra `backend\bin\caserunner.exe`; `GOOS=windows GOARCH=amd64 scripts/build.sh` build chéo file `.exe` đó từ Linux.

Binary build bằng `go build` thường, không qua script, vẫn phục vụ API; khi đó `/` trả `503` kèm ghi chú FE chưa được build. Lúc phát triển, Vite dev server (`npm run dev`, cổng 5173) chuyển tiếp `/api` sang backend (`CASERUNNER_API_URL`, mặc định `http://127.0.0.1:8080`).

| Công cụ | Phiên bản |
|---|---|
| Go | 1.27+ |
| Node.js | 20.19+ hoặc 22.12+ (chỉ để build) |
| gcc | chỉ cho `go test -race` |

Cách tester dùng tool: [hướng dẫn sử dụng](../user-guide.vi.md).
