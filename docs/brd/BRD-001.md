## 1. Goals

A tool that lets a **tester** test an API with many data sets without writing code:

1. The tester pastes a `curl` command (for example, copied from Postman or Chrome DevTools).
2. The tool extracts the method, URL, headers, and body, and **lists the fields** of the JSON body.
3. For each field, the tester chooses **Required** or **Unrequired** (dropdown).
4. Right below the curl, the tester enters **N test cases** in an editable table, clicking **`+`** for each new row; each case has an expected outcome `PASS` or `FAIL` (§8).
5. The tool **fires** each data set; each set runs on **one goroutine/thread** through a bounded worker pool.
6. Results are returned to the tester **in real time**: `SUCCESS` (the API behaved as expected) / `FAILED` (it did not) / `EXCEPTION` / `BLOCKED`.
7. The tester **exports a report** as Excel or PDF.

### Out of scope (v1)

- No database. All data for a run lives in memory and expires after a TTL.
- No Kafka, Redis, or microservices; no login or user management.
- Not a load-testing tool. Concurrency is deliberately limited.
- No automatic retry (see §11.2; this is a safety measure for payment APIs).
- v1 supports **JSON** bodies only. `form-urlencoded`, `multipart`, and file upload come later.

## 2. Settled decisions

| # | Decision |
|---|----------|
| D1 | The input is a `curl` command. The BE parses out the method, URL, headers, and body. |
| D2 | The JSON body is flattened into a list of field paths such as `data.account.id`; arrays use the form `items[0].sku`. |
| D3 | Each field has a **Required / Unrequired** dropdown. Default: `Required`. |
| D4 | A test set that **leaves a Required field empty** → **BLOCKED, not fired**, with the warning: *"Field `data.amount` is Required. Enter a value or change it to Unrequired."* |
| D5 | An empty **Unrequired** field → **the field is removed from the request** (the key is not sent). |
| D6 | Each test set runs on one goroutine, through a **worker pool bounded at N**, and every request has a **timeout**. |
| D7 | Results are classified as `SUCCESS`, `FAILED`, `EXCEPTION`, `BLOCKED` (plus `CANCELLED`, §12). |
| D8 | Results are pushed to the FE in real time via **SSE** (one-way, server → client). |
| D9 | **No DB.** Runs are stored in memory with a TTL. Reloading the page or restarting the server loses the results, so the tester must export a file. |
| D10 | Reports are exported as **Excel (.xlsx)** and **PDF**. |
| D11 | The FE supports **export/import of the configuration** (curl + rules + test data) as a JSON file for reuse. This is done entirely in the FE; the BE stores nothing. |
| D12 | FE: **React + TypeScript + Vite + Ant Design**. BE: a single monolith. |
| D13 | BE language: **Go** (settled from OD1). Libraries per §3.1. |
| D14 | Pass/fail is decided by the **HTTP status code only** (settled from OD2). A response with any **2xx** status = actual outcome `PASS`; any other status (1xx, 3xx, 4xx, 5xx) = actual `FAIL`. No body assertions in v1. |
| D15 | Each case carries an **expected outcome**: `PASS` (the API should return a 2xx status) or `FAIL` (the API should return a non-2xx status). Empty = `PASS`. The case is `SUCCESS` when the actual outcome equals the expected one, `FAILED` otherwise (§12). |
| D16 | Test cases are entered **only in the UI**: after Analyze, the configuration appears below the curl, and **`+`** adds a numbered row (`1.`, `2.`, `3.` …) with one column per field plus `expected` (§8). No test data file is generated or imported. |
| D17 | Service name: **CurlCase** (module `curlcase`, env prefix `CURLCASE_`), part of project APIProbe (settled from OD3). |
| D18 | Backend follows **Clean Architecture**: `domain` ← `usecase` ← `adapter`, wired in `cmd/curlcase` (§14). |

## 3. Tech stack and open decisions

### 3.1 Go libraries (D13)

| Concern | Choice |
|---|---|
| "1 set = 1 goroutine" model | goroutines + a worker pool using a channel semaphore or `errgroup` |
| HTTP server | `net/http` (Go 1.22+ has method-based routing) or `chi` |
| HTTP client | `net/http` `Client` + `context.WithTimeout` |
| SSE | hand-written with `http.Flusher` (~30 lines) |
| JSON parsing that preserves order and number types | `encoding/json` + `UseNumber()` |
| Excel | `github.com/xuri/excelize/v2` |
| PDF | `github.com/go-pdf/fpdf` or `github.com/johnfercher/maroto/v2` |
| Curl splitting | hand-written tokenizer (§6) |
| Packaging | one static binary; the FE build can be embedded with `embed` |

OD1 (Go vs Java), OD2 (pass/fail criteria) and OD3 (name) are settled as D13, D14–D15 and D17; OD4 is settled as listed below.

### OD4. Minor points (settled: proposed defaults accepted)

| Point | Decision |
|---|---|
| The tester **intentionally** wants to send an empty string or `null` (as opposed to "left empty") | Special tokens: `<EMPTY>` → `""`, `<NULL>` → `null`. A truly empty cell = "not entered". |
| Can the tester change **headers / query params** per set? | v1: **JSON body fields only**. Headers and query stay as in the curl. |
| Default / maximum concurrency | default **5**, maximum **20** (configurable) |
| Per-request timeout | default **30s**; the tester can adjust it within 1–120s |
| Maximum test sets per run | **1000** |
| Target host allowlist (prevents accidentally hitting production) | Config `CURLCASE_ALLOWED_HOSTS`. Empty = allow all (local use only). See §13. |

## 5. End-to-end business flow

```
Tester pastes curl
   ↓
[1] POST /api/parse → CurlParser → {method, url, headers, bodyTemplate}
   ↓                 syntax error → 400 + message pointing to the exact position
[2] FieldExtractor flattens the body → [{path, type, sampleValue}]
   ↓
[3] FE shows the configuration below the curl: field rules (default Required)
    and a case table with one pre-filled row
   ↓
[4] Tester clicks + for each new case and fills in name, a value per field,
    and expected PASS/FAIL (§8)
   ↓
[5] FE may pre-validate to warn early, but the BE is the source of truth
   ↓
[6] POST /api/runs → BE validates each case:
       - Required left empty → BLOCKED (not fired)
       - value cannot be coerced to the field's type → BLOCKED
       - valid → build the request
    returns {runId} immediately (202); firing runs in the background
   ↓
[7] FE opens SSE GET /api/runs/{runId}/events
   ↓
[8] Worker pool fires the valid cases (at most N in parallel, timeout per request)
   ↓
[9] Each finished case → classify → save to RunStore → push SSE event "case"
   ↓
[10] All finished → SSE event "done" with a summary
   ↓
[11] Tester clicks Export → GET /api/runs/{runId}/export?format=xlsx|pdf
```

## 6. Curl Parser (specification)

### 6.1 Input

The text of a curl command, possibly multi-line. Both common copy styles must be supported:
- **bash**: line continuation with `\` + newline, strings in `'...'` or `"..."`.
- **Windows cmd** (Chrome "Copy as cURL (cmd)"): line continuation with `^` + newline, escaping with `^"`. v1 should support it; if it proves too complex, return a clear error: *"Please use 'Copy as cURL (bash)'"*.

### 6.2 Tokenizer

Hand-write a simple shell-style tokenizer (it does not execute a shell and does not expand `$VAR`):
- Drop `\`+newline (bash) or `^`+newline (cmd).
- Inside `'...'`: keep everything exactly as is.
- Inside `"..."`: handle the escapes `\"` and `\\`.
- Outside quotes: split on whitespace.
- The first token must be `curl`; otherwise → error.

### 6.3 Supported flags

| Flag | Handling |
|---|---|
| `-X`, `--request` | method |
| `-H`, `--header` | header `Name: value` (order preserved, duplicate names allowed) |
| `-d`, `--data`, `--data-raw`, `--data-binary`, `--data-ascii` | body. Multiple `-d` → joined with `&` (as curl does). If it starts with `@` (read from file) → "not supported" error |
| `--json` | body + automatically adds `Content-Type`/`Accept: application/json` |
| `--url` or a non-flag token | URL |
| `-u`, `--user` | converted to an `Authorization: Basic ...` header |
| `-k`, `--insecure` | record `insecure=true`; see §13 |
| `--compressed`, `-L`, `--location`, `-s`, `-v`, `-i` | ignored (with a soft warning in `warnings[]`) |
| Any other unknown flag | do not fail; add it to `warnings[]` |

Method rule: if `-X` is present, use it; if there is no `-X` but there is a body, use `POST`; otherwise `GET`.

### 6.4 Output

```json
{
  "method": "POST",
  "url": "https://uat-api.example.com/v1/transfers?channel=MB",
  "headers": [
    {"name": "Content-Type", "value": "application/json"},
    {"name": "Authorization", "value": "Bearer eyJ..."}
  ],
  "bodyRaw": "{\"data\":{\"amount\":100000,...}}",
  "bodyKind": "json",
  "insecure": false,
  "warnings": ["Ignored flag --compressed"]
}
```

`bodyKind`: `none` | `json` | `unsupported`. A body that exists but cannot be parsed as JSON → `unsupported`; the FE shows *"v1 supports JSON bodies only"* and does not allow running.

## 7. Field Extractor (JSON flattening)

### 7.1 Rules

- List **leaves** only (string, number, boolean, null). Empty objects/arrays are also treated as leaves (type `object`/`array`) so the tester knows they exist.
- Paths: objects use `.`, arrays use `[i]`. Examples: `data.account.id`, `items[0].sku`.
- A key containing `.` or `[` → escape it as `["key.with.dot"]`. (Rare, but it must not corrupt the path.)
- Preserve the **key order** of the original body (do not decode into a `map`; read with `json.Decoder.Token()` or use an order-preserving library).
- Numbers: keep the literal text form (`json.Number`); do **not** convert to float64 (amounts and long account numbers would lose precision).

### 7.2 Example

Body:
```json
{
  "requestId": "REQ001",
  "data": {
    "amount": 100000,
    "account": {"id": "0123456789", "type": "SAVING"},
    "note": "test",
    "urgent": false
  },
  "items": [{"sku": "A1", "qty": 2}]
}
```

Output:
| path | type | sampleValue |
|---|---|---|
| `requestId` | string | `REQ001` |
| `data.amount` | number | `100000` |
| `data.account.id` | string | `0123456789` |
| `data.account.type` | string | `SAVING` |
| `data.note` | string | `test` |
| `data.urgent` | boolean | `false` |
| `items[0].sku` | string | `A1` |
| `items[0].qty` | number | `2` |

## 8. Test case table (UI)

There is no test data file to generate or import. As soon as the curl is analyzed (§6, §7), the **configuration appears directly below the curl input** on the same page: the field rules, then an editable test case table. The tester clicks **`+`** to add a row and fills in one case per row.

### 8.1 Columns

The table is built from the parsed fields; its columns are fixed once the curl is analyzed:

| Column | Content | Empty cell |
|---|---|---|
| `#` | Case number `1.`, `2.`, `3.` …, assigned automatically in row order and renumbered when rows are deleted or reordered. Not editable. | — |
| `name` | Free-text case name | `Case <n>` |
| one column per field path (§7), in body order; the header shows the path, its type and a Required/Unrequired tag | The value to send. Same cell rules as §9: `<EMPTY>` → `""`, `<NULL>` → `null` | not entered: Required → BLOCKED, Unrequired → key removed |
| `expected` | `Select`: `PASS` (the API should return a 2xx status) or `FAIL` (the API should return any non-2xx status) | `PASS` |
| actions | Duplicate row, delete row | — |

Example, for the §7.2 body with `data.note` set to Unrequired:

| # | name | requestId | data.amount | data.account.id | … | data.note | … | expected |
|---|---|---|---|---|---|---|---|---|
| 1. | Valid transfer | REQ001 | 100000 | 0123456789 | … | test | … | PASS |
| 2. | Amount is zero | REQ002 | 0 | 0123456789 | … | test | … | FAIL |
| 3. | Note omitted | REQ003 | 50000 | 0123456789 | … | | … | PASS |
| 4. | Account id missing | REQ004 | 50000 | | … | test | … | FAIL |
| **`+`** | | | | | | | | |

Case 3 sends no `data.note` key (Unrequired, empty). Case 4 is **BLOCKED** and not fired, because `data.account.id` is Required, even though it expects `FAIL`; to test the API's own validation of a missing account id, the tester sets that field to Unrequired first (§9 note).

### 8.2 Behavior

- **`+`** appends a new row **pre-filled with the curl's sample values** and `expected = PASS`, so a new case starts from a working request and the tester changes only what the case is about. The table starts with one such row after Analyze.
- **Duplicate** copies a row below itself; **delete** removes it. Both renumber `#`.
- Cells are plain text inputs; `<EMPTY>` and `<NULL>` can be typed as is.
- Changing a field's rule (Required ↔ Unrequired) updates the column tag and the pre-validation immediately; the values already entered are kept.
- Analyzing a **different** curl rebuilds the columns. Values are kept for field paths that still exist; the tester is asked to confirm first when rows would lose data.
- The `+` button is disabled at `CURLCASE_MAX_CASES` rows (default 1000); the BE enforces the same limit (§13).

## 9. Validator

Runs in the BE for **each case** before firing. A case may have **multiple errors**; collect them all and report them at once.

Conventions for cell values entered by the tester (always strings):
- `""` (empty) = **not entered**.
- `<EMPTY>` = send the empty string `""` (per OD4).
- `<NULL>` = send `null` (per OD4).
- Anything else = a value to be coerced to the field's type.

| Condition | Result |
|---|---|
| **Required** field + empty cell | error `REQUIRED_MISSING`: *"Field `data.amount` is Required. Enter a value or change it to Unrequired."* |
| **Unrequired** field + empty cell | valid; the field will be **removed** from the request |
| type `number` and the value is not a valid number | error `TYPE_MISMATCH`: *"Field `data.amount` expects type number, got 'abc'"* |
| type `boolean` and the value is not `true`/`false` | error `TYPE_MISMATCH` |
| type `string` | always valid |
| `<NULL>` | valid for every type (the tester deliberately tests null) |
| `expected` is not `PASS` or `FAIL` (empty = `PASS`, §8.1) | error `INVALID_EXPECTATION` |

Any error → the case becomes **BLOCKED**, `errors[]` is recorded, and it is **not fired**.

> Note: to test whether the API validates a "missing field", the tester switches that field to **Unrequired** and leaves it empty. The request will omit the field; set `expected = FAIL`.

## 10. Request Builder

For each valid case:

1. **Deep clone** the body template (the template shared across goroutines must never be mutated).
2. For each field:
   - has a value → set it at the path with the correct type (`number` is written as a JSON number, not quoted).
   - Unrequired + empty → **delete the key** from its parent object.
     - If the path is inside an array (`items[0].sku`) → delete the `sku` key in that element; do **not** delete the array element.
     - If the parent object becomes empty → keep `{}` (no cascading deletion upward).
3. Re-serialize the JSON, preserving the original key order.
4. Method, URL, and headers stay as in the curl. `Content-Length` is recalculated (the HTTP client does this; do not copy the `Content-Length` header from the curl).

Store the built `requestBody` in the result so the tester can compare it in the report.

## 11. Runner (worker pool)

### 11.1 Model (Go)

```
POST /api/runs
   ↓
create Run{status: RUNNING}, save to RunStore, return 202 {runId}
   ↓
go runner.Execute(ctx, run)        // ctx is tied to the run, not to the HTTP request
   ↓
sem := make(chan struct{}, concurrency)
for each valid case:
    sem <- struct{}{}               // blocks while N goroutines are running
    go func(c) {
        defer func(){ <-sem }()
        defer recover()             // a panic in one case must not crash the whole run
        reqCtx, cancel := context.WithTimeout(ctx, timeout)
        defer cancel()
        result := send(reqCtx, c)
        result = classify(result)
        run.Save(result)            // mutex-protected
        broker.Publish(runId, result)
    }(c)
wait for all → run.status = DONE → publish "done"
```

`golang.org/x/sync/errgroup` with `SetLimit(n)` may replace the hand-written semaphore, but **do not** let one case's error cancel the other cases (a case error is result data, not a group error).

### 11.2 Mandatory rules

- **No retry.** A payment/transfer API may already have committed even if the client timed out. Retrying could create duplicate transactions. A timeout is recorded as `EXCEPTION` with `errorType = TIMEOUT` and the note *"Cannot determine whether the server processed the request"*.
- Use **one** shared `http.Client` for the whole app (connection pooling); do not create a new client per request. `CheckRedirect` returns `http.ErrUseLastResponse` (do not follow redirects automatically, so the tester sees 3xx).
- Read at most **1 MB** of the response body (`io.LimitReader`); truncate the rest and mark `truncated=true`.
- Always `resp.Body.Close()`.
- Measure `durationMs` from sending until the body is fully read.
- Completion order does **not** follow case order. Each result carries `caseIndex` so the FE and the report can re-sort.
- Support **run cancellation**: `POST /api/runs/{id}/cancel` → cancel the run's `ctx`. Cases not yet started → `CANCELLED`; cases in flight → `EXCEPTION` (`errorType = CANCELLED`).

## 12. Result Classifier

Every fired case gets an **actual outcome** from the HTTP status alone (D14):

| HTTP status received | Actual outcome |
|---|---|
| any `2xx` (`200`, `201`, `202`, `204`, …) | `PASS` |
| anything else (1xx, 3xx, 4xx, 5xx) | `FAIL` |

The case status then compares the actual outcome with the case's `expected` (D15):

| Status | Condition |
|---|---|
| `BLOCKED` | The Validator reported errors; the case was not fired |
| `EXCEPTION` | No valid HTTP response was received: timeout, connection refused, DNS error, TLS error, malformed response, cancelled. There is no actual outcome |
| `SUCCESS` | actual outcome = `expected` (expected `PASS` and got 2xx, or expected `FAIL` and got non-2xx) |
| `FAILED` | actual outcome ≠ `expected` |
| `CANCELLED` | The run was cancelled before the case was fired |

Check order: BLOCKED → EXCEPTION → compare outcomes. The response body is stored and shown, but never affects the status in v1.

Each result has a tester-friendly `reason`, for example:
- `"Expected PASS (2xx), got HTTP 400"`
- `"Expected FAIL (non-2xx), got HTTP 201"`
- `"Expected FAIL, got HTTP 400 as expected"`
- `"Timed out after 30s. Cannot determine whether the server processed the request"`
- `"Could not connect to uat-api.example.com:443 (connection refused)"`

`errorType` for EXCEPTION: `TIMEOUT` | `CONNECTION` | `DNS` | `TLS` | `INVALID_RESPONSE` | `CANCELLED` | `INTERNAL`.

## 13. Safety & security

This tool sends requests to arbitrary URLs based on input, so it needs guardrails:

1. **Host allowlist**: env `CURLCASE_ALLOWED_HOSTS` (e.g. `localhost,*.uat.example.com,10.10.*`). A host that does not match → `POST /api/runs` returns 400 *"Host is not in the allowlist"*. Empty = allow all, and log a warning at startup.
2. **Limits**: maximum concurrency, maximum cases, maximum timeout (OD4). The BE always clamps the values sent by the FE.
3. **`-k/--insecure`**: TLS verification is skipped only when env `CURLCASE_ALLOW_INSECURE=true`. Otherwise return a clear error. The system trust store is used by default. In corporate environments with an internal CA, install the CA into the trust store instead of disabling verification.
4. **Masking**: in server logs and **in exported reports**, mask the values of the `Authorization`, `Cookie`, `X-Api-Key` headers and any header containing `token`/`secret`, keeping only the first 6 characters + `***`. The results UI also masks them by default.
5. **Do not log** request/response bodies at INFO level (they may contain customer data). Log only `runId`, `caseIndex`, status, and duration.
6. By default the server binds only to `127.0.0.1`. To let the whole team use it, configure `CURLCASE_BIND`.

## 14. Directory layout

### 14.1 Backend: Clean Architecture (D18)

Dependencies point inward only: `adapter` → `usecase` → `domain`. `cmd/curlcase/main.go` is the composition root and the only place that knows every layer.

| Layer | Holds | May import |
|---|---|---|
| `domain` | Entities and pure business rules: curl parsing, field flattening, validation, request building, classification. No I/O, no goroutines, no clock, no `net/http`. | standard library only |
| `usecase` | Application rules: one use case per file (parse curl, start/get/cancel/watch a run, export a report), the worker pool (§11), the host allowlist and limits (§13). Declares the **ports** (interfaces) it needs. | `domain` |
| `adapter` | Implementations of the ports and the inbound HTTP API: handlers + SSE, the outgoing HTTP sender, the in-memory run store, the event broker, the report renderers. | `usecase`, `domain`, third-party libraries |
| `config` | Env → `Config` (§20). | standard library only |

Ports are small interfaces declared in `usecase/ports.go`, next to the code that consumes them (idiomatic Go): `RunRepository`, `RequestSender`, `EventPublisher`, `ReportRenderer`, `Clock`, `IDGenerator`. No interface is declared for anything with a single implementation that tests do not need to replace.

```
curlcase/
├── backend/
│   ├── cmd/
│   │   ├── curlcase/main.go          # composition root: config → adapters → use cases → HTTP server
│   │   └── mockapi/main.go           # dev-only fake API (§18, Step 5)
│   ├── internal/
│   │   ├── config/                   # env → Config (§20)
│   │   ├── domain/
│   │   │   ├── curl/                 # RequestTemplate, tokenizer + parser (§6)
│   │   │   ├── field/                # Field, FieldRule, flatten + set/delete by path (§7, §10)
│   │   │   ├── testcase/             # Case, Validator (§9), RequestBuilder (§10)
```

## 15. API & data model

### 15.1 Endpoints

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/parse` | Parse curl → request template + field list |
| `POST` | `/api/runs` | Create a run and start firing. Returns `202 {runId}` |
| `GET` | `/api/runs/{runId}` | Current snapshot (used when the SSE connection drops) |
| `GET` | `/api/runs/{runId}/events` | SSE stream |
| `POST` | `/api/runs/{runId}/cancel` | Cancel the run |
| `GET` | `/api/runs/{runId}/export?format=xlsx\|pdf` | Download the report |
| `GET` | `/api/health` | Health check |

Common error format:
```json
{ "error": { "code": "CURL_PARSE_ERROR", "message": "Missing closing ' at position 57" } }
```

### 15.2 `POST /api/parse`

Request:
```json
{ "curl": "curl -X POST 'https://...' -H 'Content-Type: application/json' -d '{...}'" }
```
Response 200:
```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json", "insecure": false },
  "fields": [
    { "path": "data.amount", "type": "number", "sampleValue": "100000" }
  ],
  "warnings": []
}
```

### 15.3 `POST /api/runs`

The BE is stateless between parse and run: the FE sends the whole template again (the BE does not need to remember the parse result).

```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json" },
  "fields": [
    { "path": "data.amount",     "type": "number", "rule": "REQUIRED" },
    { "path": "data.note",       "type": "string", "rule": "UNREQUIRED" }
  ],
  "cases": [
    {
      "no": 1,
      "name": "Valid transfer",
      "values": { "data.amount": "50000", "data.note": "" },
      "expected": "PASS"
    }
  ],
  "options": { "concurrency": 5, "timeoutMs": 30000 }
}
```
Response `202`:
```json
{ "runId": "r_8f3a...", "total": 1, "blocked": 0 }
```

### 15.4 Result model

```go
type CaseStatus string // SUCCESS | FAILED | EXCEPTION | BLOCKED | CANCELLED | PENDING | RUNNING

type CaseResult struct {
    CaseIndex      int               `json:"caseIndex"`
    CaseNo         int               `json:"caseNo"`                   // the # shown in the case table (§8.1)
    Name           string            `json:"name"`
    Status         CaseStatus        `json:"status"`
    Reason         string            `json:"reason"`
    Errors         []ValidationError `json:"errors,omitempty"`     // when BLOCKED
    ErrorType      string            `json:"errorType,omitempty"`  // when EXCEPTION
    Input          map[string]string `json:"input"`
    RequestBody    string            `json:"requestBody,omitempty"`
    Expected       string            `json:"expected"`                 // PASS | FAIL
    Actual         string            `json:"actual,omitempty"`         // PASS | FAIL; empty when not fired or EXCEPTION
    HTTPStatus     int               `json:"httpStatus,omitempty"`
    ResponseBody   string            `json:"responseBody,omitempty"`
    Truncated      bool              `json:"truncated,omitempty"`
    StartedAt      time.Time         `json:"startedAt"`
    DurationMs     int64             `json:"durationMs"`
}

type ValidationError struct {
    Field   string `json:"field"`
    Code    string `json:"code"`    // REQUIRED_MISSING | TYPE_MISMATCH | INVALID_EXPECTATION
    Message string `json:"message"`
}

type Run struct {
    ID        string
    Status    string        // RUNNING | DONE | CANCELLED
    CreatedAt time.Time
    Template  RequestTemplate
    Fields    []FieldRule
    Results   []CaseResult  // index = caseIndex
    Summary   Summary       // counts by status
    mu        sync.Mutex
    cancel    context.CancelFunc
}
```

### 15.5 SSE events

```
event: snapshot      # sent immediately on connect: the full current state
data: {"runId":"...","status":"RUNNING","results":[...],"summary":{...}}

event: case          # whenever a case has a result
data: {CaseResult}

event: done
data: {"runId":"...","status":"DONE","summary":{"total":10,"success":6,"failed":2,"exception":1,"blocked":1,"cancelled":0}}
```

- Sending `snapshot` first means a client that connects late or reconnects loses no data. `Last-Event-ID` is not needed.
- Send a `: ping` heartbeat comment every 15s so proxies (Nginx) do not cut the connection. Headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
- Publishing must not block workers: each subscriber has a buffered channel; when it is full, drop that subscriber (the client will reconnect and receive a snapshot).

### 15.6 RunStore

- `map[string]*Run` + `sync.RWMutex`.
- Default TTL of **1 hour** after a run finishes (`CURLCASE_RUN_TTL`). A janitor goroutine cleans up every minute.
- At most **50 runs** in memory. When exceeded, delete the oldest DONE run. If all are RUNNING → `429`.
- Expired run → `GET` / `export` returns `404` *"Run has expired, please run it again"*.

## 16. FE (React + TS + Vite + Ant Design)

A **single page**; each panel appears below the previous one as the tester moves on, so the curl stays visible while cases are entered. All state is kept in React (`useReducer` or Zustand; no Redux needed).

**Curl panel.** `Input.TextArea` + an "Analyze" button. Shows parse errors and `warnings`. Has an **Import config (.json)** button to reload a previous session.

**Configuration panel** (appears below after Analyze):
- Request summary: method + URL + headers (Authorization masked) for the tester to confirm.
- **Field rules**: `Table` with Field path | Type | Sample value | Rule (`Select` Required/Unrequired), plus "All Required" / "All Unrequired" buttons.
- **Case table** (§8): one pre-filled row, a **`+`** button to add rows, duplicate / delete per row.
- FE pre-validation: an empty Required cell is highlighted red with a tooltip carrying the exact warning from D4. Running is still allowed (that case will be BLOCKED), but a confirmation is shown: *"X cases will be blocked. Run anyway?"*.
- Run options: concurrency (InputNumber 1–20), timeout (seconds).
- **Run** button, and **Export config (.json)**: `{version:1, curl, fields(rules), cases, options}`.

**Results panel** (appears below after Run):
- Summary bar: Total / SUCCESS (green) / FAILED (red) / EXCEPTION (orange) / BLOCKED (gray) + `Progress`.
- `Table` sorted by `caseIndex`, columns: #, Name, Expected, HTTP, Status (colored `Tag`), Duration, Reason. Clicking a row → a `Drawer` showing input, request body, response body (pretty JSON), expected vs actual outcome.
- Filter by status.
- **Cancel run**, **Export Excel**, **Export PDF**, **Run again** (keeps the configuration) buttons. Editing the configuration and running again replaces the results panel.
- Persistent warning: *"Results are kept only for X minutes. Export a file if you need to keep them."*

## 17. Report export

### Excel (.xlsx)

- **"Summary" sheet**: tool name, run time, method + URL, concurrency, timeout, a count table by status, and the field rules table.
- **"Results" sheet**: one row per case. A4 landscape. Page 1: the summary as above. Then a compact results table (#, name, expected, HTTP, status, duration, reason). The PDF does **not** print full request/response bodies (too long). Use Excel for details.

Both mask sensitive headers (§13). File name: `curlcase_<runId>_<yyyyMMdd_HHmmss>.xlsx|pdf`.

## 19. Testing

- **Unit**: the `domain` packages (curl, field, testcase, run classifier). This is where the business rules live and needs the most thorough testing.
- **Use case**: `usecase` with in-memory fakes of its ports (worker pool, cancel, limits).
- **Integration**: `adapter/sender` + `httptest.Server`; `adapter/httpapi` handlers with `httptest.NewRecorder`.
- **Race**: always run `go test -race ./...` (worker pool, memstore, broker).
- **Manual E2E**: FE + BE + mockapi, 50 cases, concurrency 5, with a few BLOCKED/timeout cases.

Critical cases that must not be missed:
1. Required field left empty → BLOCKED, and **no** request reaches the fake server (count hits).
2. Unrequired field left empty → the request does **not contain** that key.
3. Large numbers / amounts keep full precision in the sent request.
4. Timeout → EXCEPTION/TIMEOUT, **no** retry (the fake server receives exactly 1 hit).
5. The number of concurrent requests never exceeds `concurrency`.
6. A panic in one case does not crash the run.
7. Cancelling a run midway → cases not yet started are CANCELLED.
8. Any 2xx is an actual `PASS`: expected `PASS` + 201 → SUCCESS; expected `PASS` + 302 → FAILED; expected `FAIL` + 400 → SUCCESS.
9. A row added with `+` and left unchanged produces a request identical to the curl's original body.
