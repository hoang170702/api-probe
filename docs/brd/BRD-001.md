## 1. Goals

A tool that lets a **tester** test an API with many data sets without writing code:

1. The tester pastes a `curl` command (for example, copied from Postman or Chrome DevTools).
2. The tool extracts the method, URL, headers, and body, and **lists the fields** of the JSON body.
3. For each field, the tester chooses **Required** or **Unrequired** (dropdown).
4. Right below the curl, the tester enters **N test cases** in an editable table, clicking **`+`** for each new row; each case has an **expect** code that must appear in the response (§8).
   When the API needs a token, the tester adds optional **prepare steps** (e.g. a login curl); the token they return is put into the main curl automatically (§11.3).
5. The tool **fires** each data set; each set runs on **one goroutine/thread** through a bounded worker pool.
6. Results are returned to the tester **in real time**: `SUCCESS` (the expect code was found in the response) / `FAILED` (it was not) / `EXCEPTION` / `BLOCKED`.
7. The tester **exports a report** as Excel or PDF.

### Out of scope (v1)

- No database. All data for a run lives in memory and expires after a TTL.
- No Kafka, Redis, or microservices; no login or user management.
- Not a load-testing tool. Concurrency is deliberately limited.
- No automatic retry (see §11.2; this is a safety measure for payment APIs).
- v1 supports **JSON** bodies only. `form-urlencoded`, `multipart`, and file upload come later.

## 2. Settled decisions

| # | Decision |
|---|----------|
| D1 | The input is a `curl` command. The BE parses out the method, URL, headers, and body. |
| D2 | The JSON body is flattened into a list of field paths such as `data.account.id`; arrays use the form `items[0].sku`. |
| D3 | Each field has a **Required / Unrequired** dropdown. Default: `Required`. |
| D4 | A test set that **leaves a Required field empty** → **BLOCKED, not fired**, with the warning: *"Field `data.amount` is Required. Enter a value or change it to Unrequired."* |
| D5 | An empty **Unrequired** field → **the field is removed from the request** (the key is not sent). |
| D6 | Each test set runs on one goroutine, through a **worker pool bounded at N**, and every request has a **timeout**. |
| D7 | Results are classified as `SUCCESS`, `FAILED`, `EXCEPTION`, `BLOCKED` (plus `CANCELLED`, §12). A failed prepare step makes the case `EXCEPTION` with `errorType = PREPARE_FAILED`. |
| D8 | Results are pushed to the FE in real time via **SSE** (one-way, server → client). |
| D9 | **No DB.** Runs are stored in memory with a TTL. Reloading the page or restarting the server loses the results, so the tester must export a file. |
| D10 | Reports are exported as **Excel (.xlsx)** and **PDF**. |
| D11 | The FE supports **export/import of the configuration** (curl + rules + test data) as a JSON file for reuse. This is done entirely in the FE; the BE stores nothing. |
| D12 | FE: **React + TypeScript + Vite + Ant Design**. BE: a single monolith. |
| D13 | BE language: **Go** (settled from OD1). Libraries per §3.1. |
| D14 | Pass/fail is decided by the **expect code** only (v0.7; replaces the 2xx rule settled from OD2; status matching refined in v0.8). The code matches the HTTP status only when it **is** the status code (`401` ↔ HTTP 401); otherwise it is searched, case-sensitively, in the whole body read (up to 1 MB) and then in every response header as `Name: value`, except transport headers (`Date`, `Content-Length`, `Content-Type`, `Server`, `Connection`, `ETag`, `Last-Modified`, `Expires`, `Cache-Control`, `Vary`, `Transfer-Encoding`, `Keep-Alive`, `Age`), whose values would match short codes by accident. The case is `SUCCESS` when it is found, `FAILED` otherwise. The HTTP status does not decide on its own: many APIs return 200 with an error code in the body. A short code can match inside another body value (`00` occurs in `100000`), so testers should prefer distinctive codes such as `"code":"00"`; it never matches a status by being part of it (`00` does not match HTTP 200 or 500). |
| D15 | Every case **must** have an expect code; an empty one makes the case `BLOCKED` (`INVALID_EXPECTATION`). There is no `PASS`/`FAIL` column. |
| D16 | Test cases are entered **only in the UI**: after Analyze, the configuration appears below the curl, and **`+`** adds a numbered row (`1.`, `2.`, `3.` …) with one column per field plus `expect` (§8). No test data file is generated or imported. |
| D17 | Service name: **API Case Runner** (module `caserunner`, env prefix `CASERUNNER_`), part of project APIProbe (settled from OD3). |
| D18 | Backend follows **Clean Architecture**: `domain` ← `usecase` ← `adapter`, wired in `cmd/caserunner` (§14). |
| D19 | The frontend build is **embedded in the Go binary**: one executable serves the UI and the API (§21). |
| D20 | **Prepare steps are optional.** When the API needs a token, the tester adds one or more prepare curls (login, OTP, …). They run in order; each step **captures** values from its response into variables (a token is found automatically, or by a path the tester gives). The main curl gets `Authorization: Bearer {{token}}` automatically (can be turned off), and `{{name}}` placeholders may be used anywhere in the URL, headers or body of the main curl and of later steps (§11.3). |
| D21 | With prepare steps, cases run **one at a time**, and the prepare steps run again **before every case**, so each case uses a fresh token. Without prepare steps, cases run in parallel as in D6. |
| D22 | The UI is available in **Vietnamese and English**, switched in the header; the choice is remembered in the browser, and the first visit follows the browser language. Messages coming from the backend (parse errors, warnings, reasons) stay in English. |

## 3. Tech stack and open decisions

### 3.1 Go libraries (D13)

| Concern | Choice |
|---|---|
| "1 set = 1 goroutine" model | goroutines + a worker pool using a channel semaphore or `errgroup` |
| HTTP server | `net/http` with Go 1.22+ method-based routing (no router library) |
| HTTP client | `net/http` `Client` + `context.WithTimeout` |
| SSE | hand-written with `http.Flusher` (~30 lines) |
| JSON parsing that preserves order and number types | `encoding/json` + `UseNumber()` |
| Excel | `github.com/xuri/excelize/v2` |
| PDF | `github.com/go-pdf/fpdf` or `github.com/johnfercher/maroto/v2` |
| Curl splitting | hand-written tokenizer (§6) |
| Packaging | one binary; the FE build is embedded with `embed` (D19) |

OD1 (Go vs Java), OD2 (pass/fail criteria, redefined in v0.7) and OD3 (name) are settled as D13, D14–D15 and D17; OD4 is settled as listed below.

### OD4. Minor points (settled: proposed defaults accepted)

| Point | Decision |
|---|---|
| The tester **intentionally** wants to send an empty string or `null` (as opposed to "left empty") | Special tokens: `<EMPTY>` → `""`, `<NULL>` → `null`. A truly empty cell = "not entered". |
| Can the tester change **headers / query params** per set? | v1: **JSON body fields only**. Headers and query stay as in the curl. |
| Default / maximum concurrency | default **5**, maximum **20** (configurable) |
| Per-request timeout | default **30s**; the tester can adjust it within 1–120s |
| Maximum test sets per run | **1000** |
| Target host allowlist (prevents accidentally hitting production) | Config `CASERUNNER_ALLOWED_HOSTS`. Empty = allow all (local use only). See §13. |

## 5. End-to-end business flow

```
Tester pastes curl
   ↓
[1] POST /api/parse → CurlParser → {method, url, headers, bodyTemplate}
   ↓                 syntax error → 400 + message pointing to the exact position
[2] FieldExtractor flattens the body → [{path, type, sampleValue}]
   ↓
[3] FE shows the configuration below the curl: field rules (default Required)
    and a case table with one pre-filled row
   ↓
[4] Tester clicks + for each new case and fills in name, a value per field,
    and the expect code (§8); optionally adds prepare steps (§11.3)
   ↓
[5] FE may pre-validate to warn early, but the BE is the source of truth
   ↓
[6] POST /api/runs → BE validates each case:
       - Required left empty → BLOCKED (not fired)
       - value cannot be coerced to the field's type → BLOCKED
       - valid → build the request
    returns {runId} immediately (202); firing runs in the background
   ↓
[7] FE opens SSE GET /api/runs/{runId}/events
   ↓
[8] Worker pool fires the valid cases (at most N in parallel, timeout per request);
    with prepare steps: one case at a time, prepare steps run before each (D21)
   ↓
[9] Each finished case → classify → save to RunStore → push SSE event "case"
   ↓
[10] All finished → SSE event "done" with a summary
   ↓
[11] Tester clicks Export → GET /api/runs/{runId}/export?format=xlsx|pdf
```

## 6. Curl Parser (specification)

Package `domain/curl`. It never runs a shell and never expands `$VAR`.

### 6.1 Input

The text of a curl command, possibly multi-line, with LF or CRLF line endings. Both copy styles are supported:
- **bash** (Chrome/Firefox "Copy as cURL (bash)", Postman, hand-written).
- **Windows cmd** (Chrome "Copy as cURL (cmd)").

The style is detected from the line continuations: a line ending in `^` means cmd, a line ending in `\` means bash. A single-line command is cmd when it contains `^"`, bash otherwise.

The first word must be `curl` or `curl.exe` (case-insensitive).

### 6.2 Tokenizer

**bash:**
- `\` + newline is a line continuation and is dropped.
- Inside `'...'`: everything is kept exactly as is.
- Inside `"..."`: `\"`, `\\`, `\$` and `` \` `` are unescaped; `\` + newline is dropped; any other backslash is kept.
- Inside `$'...'` (used by Chrome when a body holds `'` or newlines): ANSI-C escapes `\n \t \r \a \b \f \v \e \\ \' \" \?`, `\xHH`, `\uHHHH`, `\UHHHHHHHH` and octal `\nnn`.
- Outside quotes: a backslash escapes the next character; whitespace separates words. Adjacent quoted and unquoted parts join into one word; `''` is an empty word.

**cmd** goes through the two layers Windows applies:
1. cmd.exe: outside its own `"..."` quotes, `^` + newline is a line continuation and `^x` becomes `x`.
2. curl.exe argument splitting (`CommandLineToArgvW` rules): whitespace separates words outside quotes; `"` toggles quoting; 2n backslashes before `"` become n and the quote toggles, 2n+1 become n plus a literal `"`; `""` inside quotes is a literal `"`; other backslashes are literal.

### 6.3 Flags

Short flags may be combined (`-sSLk`) and take attached values (`-XPOST`, `-H'X: 1'`). `--` ends the flags.

| Flag | Handling |
|---|---|
| `-X`, `--request` | method, kept as written |
| `-H`, `--header` | header `Name: value` (order preserved, duplicate names allowed). `Name;` sends an empty header. `Name:` (curl's "remove this header") and a value without `:` are ignored with a warning. `@file` → `CURL_UNSUPPORTED` |
| `-d`, `--data`, `--data-ascii`, `--data-binary` | body piece. A value starting with `@` (read from a file) → `CURL_UNSUPPORTED` |
| `--data-raw` | body piece; a leading `@` is literal, as in curl |
| `--json` | body piece; adds `Content-Type: application/json` and `Accept: application/json` unless the tester set them. `@file` → `CURL_UNSUPPORTED` |
| `-F`, `--form`, `--form-string`, `--data-urlencode` | a body v1 cannot run: `bodyKind = unsupported`, with a warning |
| `--url` or a non-flag word | URL; a second URL → `CURL_PARSE_ERROR` |
| `-u`, `--user` | `Authorization: Basic base64(user:password)`; without `:` the password is empty, with a warning |
| `--oauth2-bearer` | `Authorization: Bearer <token>` |
| `-b`, `--cookie` | `Cookie` header when the value holds `=`; otherwise it is a cookie file and is ignored with a warning |
| `-A`, `--user-agent` | `User-Agent` header |
| `-e`, `--referer` | `Referer` header (a `;auto` suffix is dropped) |
| `-k`, `--insecure` | `insecure = true`; whether it is honored is a policy decision (§13) |
| `-I`, `--head` | method `HEAD` when there is no `-X` |
| `-G`, `--get`, `-T`, `--upload-file`, `--request-target`, `--aws-sigv4` | `CURL_UNSUPPORTED`: ignoring them would send a different request than the curl |
| `-L`, `--location` | ignored with the warning *"redirects are never followed, a 3xx is reported as the result"* (§11.2) |
| `-m`, `--max-time`, `--connect-timeout` | ignored: the run's timeout applies |
| `--retry` | ignored: API Case Runner never retries |
| `-x`, `--proxy`, `--resolve`, `--connect-to` | ignored: requests go directly to the URL's host |
| `--compressed`, `-s`, `-S`, `-v`, `-i`, `-f`, `-g`, `-N`, `--http1.1`, `--http2`, `-o`, `-w`, `--cacert`, `--cert`, … (output, TLS-file and transport flags) | ignored with the warning *"Ignored <flag>"*; flags known to take a value consume it |
| Any other unknown flag | ignored with the warning *"Ignored unknown flag <flag>"*; assumed to take no value |

### 6.4 Building the template

- **Method**: `-X` if given; otherwise `HEAD` for `-I`; otherwise `POST` when there is a body; otherwise `GET`.
- **URL**: a URL without `://` gets `http://`, as curl does, with a warning. Only `http` and `https` are accepted (`CURL_UNSUPPORTED` otherwise); a URL without a host → `CURL_PARSE_ERROR`.
- **Body**: all body pieces are joined with `&` in order, as curl does, with a warning when there is more than one.
- **`bodyKind`**: `none` (no body), `json` (the body is valid JSON), `unsupported` (any other body, or a form flag). The FE shows *"v1 supports JSON bodies only"* for `unsupported` and the request cannot run.
- A JSON body without a `Content-Type` header gets a warning: the API may not read it as JSON (curl itself would send `application/x-www-form-urlencoded`).

### 6.5 Errors

A rejected command returns a `ParseError` with a code and a 1-based **character** position (not a byte offset, so text with diacritics points to the right place); the message ends with *"at position N"* when there is a position.

| Code | When | Example message |
|---|---|---|
| `CURL_PARSE_ERROR` | empty text; first word not `curl`; unterminated quote; flag without its value; no URL; two URLs; invalid URL or no host | *"Missing closing ' for the quote opened at position 9"* |
| `CURL_UNSUPPORTED` | valid curl that v1 cannot reproduce: body or headers from a file, `-G`, `-T`, `--request-target`, `--aws-sigv4`, a non-http(s) scheme, a JSON body with duplicate keys (§7) | *"-d @body.json reads the body from a file, which is not supported; paste the body itself at position 16"* |

### 6.6 Output

```json
{
  "method": "POST",
  "url": "https://uat-api.example.com/v1/transfers?channel=MB",
  "headers": [
    {"name": "Content-Type", "value": "application/json"},
    {"name": "Authorization", "value": "Bearer eyJ..."}
  ],
  "bodyRaw": "{\"data\":{\"amount\":100000,...}}",
  "bodyKind": "json",
  "insecure": false,
  "warnings": ["Ignored --compressed"]
}
```

## 7. Field Extractor (JSON flattening)

### 7.1 Rules

- List **leaves** only (string, number, boolean, null). Empty objects/arrays are also treated as leaves (type `object`/`array`) so the tester knows they exist.
- Paths: objects use `.`, arrays use `[i]`. Examples: `data.account.id`, `items[0].sku`.
- A key that is empty or contains `.`, `[`, `]`, `"` or `\` is written as a JSON-quoted bracket segment: `["key.with.dot"]`, `x[""]`. Other keys, including ones with spaces or diacritics, use the dot form.
- Preserve the **key order** of the original body (do not decode into a `map`; read with `json.Decoder.Token()` or use an order-preserving library).
- Numbers: keep the literal text form (`json.Number`); do **not** convert to float64 (amounts and long account numbers would lose precision).
- `sampleValue` is written the way a tester types a cell, so a row of samples rebuilds the original body: an empty string is `<EMPTY>`, `null` is `<NULL>`, an empty object/array is `{}`/`[]`.
- A top-level array is allowed (`[0].id`). A scalar or empty top-level body has no fields; the parse response then carries the warning *"The JSON body has no fields to vary"*.
- A body that repeats a key in one object is rejected with `CURL_UNSUPPORTED` (a path would point at two values). Nesting deeper than 512 levels is rejected the same way.

### 7.2 Example

Body:
```json
{
  "requestId": "REQ001",
  "data": {
    "amount": 100000,
    "account": {"id": "0123456789", "type": "SAVING"},
    "note": "test",
    "urgent": false
  },
  "items": [{"sku": "A1", "qty": 2}]
}
```

Output:
| path | type | sampleValue |
|---|---|---|
| `requestId` | string | `REQ001` |
| `data.amount` | number | `100000` |
| `data.account.id` | string | `0123456789` |
| `data.account.type` | string | `SAVING` |
| `data.note` | string | `test` |
| `data.urgent` | boolean | `false` |
| `items[0].sku` | string | `A1` |
| `items[0].qty` | number | `2` |

## 8. Test case table (UI)

There is no test data file to generate or import. As soon as the curl is analyzed (§6, §7), the **configuration appears directly below the curl input** on the same page: the field rules, then an editable test case table. The tester clicks **`+`** to add a row and fills in one case per row.

### 8.1 Columns

The table is built from the parsed fields; its columns are fixed once the curl is analyzed:

| Column | Content | Empty cell |
|---|---|---|
| `#` | Case number `1.`, `2.`, `3.` …, assigned automatically in row order and renumbered when rows are deleted or reordered. Not editable. | — |
| `name` | Free-text case name | `Case <n>` |
| one column per field path (§7), in body order; the header shows the path, its type and a Required/Unrequired tag | The value to send. Same cell rules as §9: `<EMPTY>` → `""`, `<NULL>` → `null` | not entered: Required → BLOCKED, Unrequired → key removed |
| `expect` | The code that must appear somewhere in the response (D14), e.g. `00`, `ERR_AMOUNT_INVALID`, `401` | not allowed: the case is BLOCKED |
| actions | Duplicate row, delete row | — |

Example, for the §7.2 body with `data.note` set to Unrequired:

| # | name | requestId | data.amount | data.account.id | … | data.note | … | expect |
|---|---|---|---|---|---|---|---|---|
| 1. | Valid transfer | REQ001 | 100000 | 0123456789 | … | test | … | `"code":"00"` |
| 2. | Amount is zero | REQ002 | 0 | 0123456789 | … | test | … | `ERR_AMOUNT_INVALID` |
| 3. | Note omitted | REQ003 | 50000 | 0123456789 | … | | … | `"code":"00"` |
| 4. | Account id missing | REQ004 | 50000 | | … | test | … | `ERR_ACCOUNT_REQUIRED` |
| **`+`** | | | | | | | | |

Cases 1 and 3 expect `"code":"00"` rather than `00`, so the success code cannot match inside an amount such as `100000` (D14). Case 3 sends no `data.note` key (Unrequired, empty). Case 4 is **BLOCKED** and not fired, because `data.account.id` is Required, even though its expect code is an error code; to test the API's own validation of a missing account id, the tester sets that field to Unrequired first (§9 note).

### 8.2 Behavior

- **`+`** appends a new row **pre-filled with the curl's sample values** and an empty `expect` the tester must fill in, so a new case starts from a working request and the tester changes only what the case is about. The table starts with one such row after Analyze.
- **Duplicate** copies a row below itself; **delete** removes it. Both renumber `#`.
- Cells are plain text inputs; `<EMPTY>` and `<NULL>` can be typed as is.
- Changing a field's rule (Required ↔ Unrequired) updates the column tag and the pre-validation immediately; the values already entered are kept.
- Analyzing a **different** curl rebuilds the columns. Values are kept for field paths that still exist; the tester is asked to confirm first when rows would lose data.
- The `+` button is disabled at `CASERUNNER_MAX_CASES` rows (default 1000); the BE enforces the same limit (§13).

## 9. Validator

Runs in the BE for **each case** before firing. A case may have **multiple errors**; collect them all and report them at once.

Conventions for cell values entered by the tester (always strings):
- `""` (empty) = **not entered**.
- `<EMPTY>` = send the empty string `""` (per OD4).
- `<NULL>` = send `null` (per OD4).
- Anything else = a value to be coerced to the field's type.

| Condition | Result |
|---|---|
| **Required** field + empty cell | error `REQUIRED_MISSING`: *"Field `data.amount` is Required. Enter a value or change it to Unrequired."* |
| **Unrequired** field + empty cell | valid; the field will be **removed** from the request |
| type `number` and the value is not a valid number | error `TYPE_MISMATCH`: *"Field `data.amount` expects type number, got 'abc'"* |
| type `boolean` and the value is not `true`/`false` | error `TYPE_MISMATCH` |
| type `string` | always valid |
| `<NULL>` | valid for every type (the tester deliberately tests null) |
| type `object` / `array` | the cell must be JSON of that kind (`{"a":1}`, `[1,2]`); otherwise `TYPE_MISMATCH` |
| type `null` (the curl sent `null`) | any JSON value; other text is sent as a string |
| the built request uses a `{{name}}` that no token step captures | error `UNKNOWN_VARIABLE`: *"Unknown variable {{otp}}: no token step captures it"* |
| `expect` is empty (D15) | error `INVALID_EXPECTATION`: *"Case needs an expect code"* |

Any error → the case becomes **BLOCKED**, `errors[]` is recorded, and it is **not fired**.

> Note: to test whether the API validates a "missing field", the tester switches that field to **Unrequired** and leaves it empty. The request will omit the field; set `expect` to the error code the API should return.

## 10. Request Builder

For each valid case:

1. **Deep clone** the body template (the template shared across goroutines must never be mutated).
2. For each field:
   - has a value → set it at the path with the correct type (`number` is written as a JSON number, not quoted).
   - Unrequired + empty → **delete the key** from its parent object.
     - If the path is inside an array (`items[0].sku`) → delete the `sku` key in that element; do **not** delete the array element.
     - If the parent object becomes empty → keep `{}` (no cascading deletion upward).
3. Re-serialize the JSON, preserving the original key order.
4. Method, URL, and headers stay as in the curl. `Content-Length` is recalculated (the HTTP client does this; do not copy the `Content-Length` header from the curl).

Store the built `requestBody` in the result so the tester can compare it in the report.

## 11. Runner (worker pool)

### 11.1 Model (Go)

```
POST /api/runs
   ↓
create Run{status: RUNNING}, save to RunStore, return 202 {runId}
   ↓
go runner.Execute(ctx, run)        // ctx is tied to the run, not to the HTTP request
   ↓
sem := make(chan struct{}, concurrency)
for each valid case:
    sem <- struct{}{}               // blocks while N goroutines are running
    go func(c) {
        defer func(){ <-sem }()
        defer recover()             // a panic in one case must not crash the whole run
        reqCtx, cancel := context.WithTimeout(ctx, timeout)
        defer cancel()
        result := send(reqCtx, c)
        result = classify(result)
        run.Save(result)            // mutex-protected
        broker.Publish(runId, result)
    }(c)
wait for all → run.status = DONE → publish "done"
```

`golang.org/x/sync/errgroup` with `SetLimit(n)` may replace the hand-written semaphore, but **do not** let one case's error cancel the other cases (a case error is result data, not a group error).

### 11.2 Mandatory rules

- **No retry.** A payment/transfer API may already have committed even if the client timed out. Retrying could create duplicate transactions. A timeout is recorded as `EXCEPTION` with `errorType = TIMEOUT` and the note *"Cannot determine whether the server processed the request"*.
- Use **one** shared `http.Client` for the whole app (connection pooling); do not create a new client per request. `CheckRedirect` returns `http.ErrUseLastResponse` (do not follow redirects automatically, so the tester sees 3xx).
- Read at most **1 MB** of the response body (`io.LimitReader`); truncate the rest and mark `truncated=true`.
- Always `resp.Body.Close()`.
- Measure `durationMs` from sending until the body is fully read.
- Completion order does **not** follow case order. Each result carries `caseIndex` so the FE and the report can re-sort.
- Support **run cancellation**: `POST /api/runs/{id}/cancel` → cancel the run's `ctx`. Cases not yet started → `CANCELLED`; cases in flight → `EXCEPTION` (`errorType = CANCELLED`).
- **Request hygiene**: the `Content-Length` and `Accept-Encoding` headers of the curl are not sent (the client sets the length and negotiates compression itself, so a gzip body copied from DevTools is still read as text); a `Host` header sets the request's host.

### 11.3 Prepare steps (optional token flow, D20–D21)

A prepare step is a curl (parsed like the main one, §6; any body kind is allowed, so a form-encoded OAuth token request works) plus a list of **captures** `{var, path}`.

1. Steps run in order. Before a step is sent, `{{name}}` placeholders in its URL, header values and body are replaced with the variables captured so far; in a JSON body the value is JSON-escaped. An unknown variable fails the step.
2. A step succeeds when the response status is 2xx **and** every capture finds a value. Otherwise it fails with a reason (*"Expected a 2xx response, got HTTP 401"*, *"token: no value at data.accessToken"*), and later steps are skipped.
3. A capture with a **path** (§7 syntax, e.g. `data.accessToken`) reads that value from the JSON response. A capture **without a path** looks for a token automatically: the first non-empty string value whose key is, in this order of preference, `access_token`, `accessToken`, `token`, `id_token`, `idToken`, `jwt`, `auth_token`, `authToken`, `session_token`, `sessionToken` (case-insensitive, at any depth). The first step's first capture is named `token` by default.
4. Before a case is sent, the same substitution is applied to the main request. With **Inject token** on (default), the main request's `Authorization` header is set to `Bearer {{token}}` (replacing any `Authorization` header from the curl, or added when there is none); with token steps and Inject token on, a run whose steps capture no variable named `token` is refused with `400` *"Inject token needs a capture named token"*.
5. During a run (D21), the steps run before every case; if they fail, that case is `EXCEPTION` with `errorType = PREPARE_FAILED` and the reason of the failed step, and the run continues with the next case.
6. Captured values are secrets: they are never logged and are masked on screen like `Authorization` (§13).

`POST /api/prepare/try` (§15.7) runs the steps once so the tester can check the captured values before running cases.

## 12. Result Classifier

Every fired case is judged by its **expect code** alone (D14): equal to the HTTP status code, or found in the body as read (up to 1 MB, §11.2), or in a response header (`Name: value`) other than the transport headers listed in D14:

| Status | Condition |
|---|---|
| `BLOCKED` | The Validator reported errors; the case was not fired |
| `EXCEPTION` | No valid HTTP response was received (timeout, connection refused, DNS error, TLS error, malformed response, cancelled), or a prepare step failed (`PREPARE_FAILED`) |
| `SUCCESS` | The expect code is the status code, or occurs in the body or an application header |
| `FAILED` | It does not |
| `CANCELLED` | The run was cancelled before the case was fired |

Check order: BLOCKED → EXCEPTION → search for the expect code. The search order is status → body → headers, and the result records where the code was found (`status`, `body` or `header`).

Each result has a tester-friendly `reason`, for example:
- `Found ERR_AMOUNT_INVALID in the body (HTTP 400)`
- `00 not found in the response (HTTP 500)` (the code is shown as typed: `Found "code":"00" in the body (HTTP 200)`)
- `"Prepare step 1 failed: Expected a 2xx response, got HTTP 401"`
- `"Timed out after 30s. Cannot determine whether the server processed the request"`
- `"Could not connect to uat-api.example.com:443 (connection refused)"`

`errorType` for EXCEPTION: `TIMEOUT` | `CONNECTION` | `DNS` | `TLS` | `INVALID_RESPONSE` | `CANCELLED` | `PREPARE_FAILED` | `POLICY` | `INTERNAL`.

## 13. Safety & security

This tool sends requests to arbitrary URLs based on input, so it needs guardrails:

1. **Host allowlist**: env `CASERUNNER_ALLOWED_HOSTS` (e.g. `localhost,*.uat.example.com,10.10.*`; `*` matches any characters, case-insensitive, the port is ignored; a pattern made only of digits, dots, colons and `*`, such as `10.10.*`, matches IP addresses only, never a domain such as `10.10.attacker.example`). It applies to every outgoing request: prepare steps and cases. A host that does not match fails that request with `errorType = POLICY` and *"Host x is not in CASERUNNER_ALLOWED_HOSTS"*. Empty = allow all, and log a warning at startup.
2. **Limits**: maximum concurrency, maximum cases, maximum timeout (OD4). The BE always clamps the values sent by the FE.
3. **`-k/--insecure`**: TLS verification is skipped only when env `CASERUNNER_ALLOW_INSECURE=true`. Otherwise the request fails with `errorType = POLICY` and a clear message. The system trust store is used by default. In corporate environments with an internal CA, install the CA into the trust store instead of disabling verification.
4. **Masking**: in server logs and **in exported reports**, mask the values of the `Authorization`, `Cookie`, `X-Api-Key` headers and any header containing `token`/`secret`, keeping only the first 6 characters + `***`. The results UI also masks them by default.
5. **Do not log** request/response bodies at INFO level (they may contain customer data). Log only `runId`, `caseIndex`, status, and duration.
6. By default the server binds only to `127.0.0.1`. To let the whole team use it, configure `CASERUNNER_BIND`.
7. **Request size**: a `POST /api/parse` body larger than 2 MB is rejected with `413 REQUEST_TOO_LARGE`. The access log records method, path, status and duration only, never headers or bodies.
8. **Browser attacks on the local server**: another web site open in the tester's browser must not drive the tool. Every request goes through a guard: a state-changing `/api/` call (`POST`) must be `application/json` (so a browser must send a CORS preflight, which is never granted) and is refused with `403 FORBIDDEN` when its `Origin` or `Sec-Fetch-Site` shows another site; with a loopback bind, a `Host` header other than `127.0.0.1`, `localhost` or `[::1]` with the bound port is refused with `403` (DNS rebinding). A network bind (`CASERUNNER_BIND=0.0.0.0:…`) skips the `Host` check and logs a warning: anyone who can reach the port can use the tool, which is accepted for use inside the company network.

## 15. API & data model

### 15.1 Endpoints

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/parse` | Parse curl → request template + field list |
| `POST` | `/api/prepare/try` | Run the prepare steps once and return what each captured (§15.7) |
| `POST` | `/api/runs` | Create a run and start firing. Returns `202 {runId}` |
| `GET` | `/api/runs/{runId}` | Current snapshot (used when the SSE connection drops) |
| `GET` | `/api/runs/{runId}/events` | SSE stream |
| `POST` | `/api/runs/{runId}/cancel` | Cancel the run |
| `GET` | `/api/runs/{runId}/export?format=xlsx\|pdf` | Download the report |
| `GET` | `/api/health` | Health check |

Paths outside `/api/` serve the embedded frontend (D19); an unknown path there returns the app's `index.html`.

Common error format:
```json
{ "error": { "code": "CURL_PARSE_ERROR", "message": "Missing closing ' for the quote opened at position 57" } }
```

| Code | HTTP | When |
|---|---|---|
| `BAD_REQUEST` | 400 | The request body is not valid JSON |
| `CURL_PARSE_ERROR` | 400 | The curl text is not a usable command (§6.5) |
| `CURL_UNSUPPORTED` | 400 | Valid curl that v1 cannot run (§6.5) |
| `FORBIDDEN` | 403 | A cross-site request, or a `Host` that is not accepted (§13 item 8) |
| `NOT_FOUND` | 404 | No API endpoint at that path |
| `RUN_NOT_FOUND` | 404 | The run is unknown or has expired: *"Run has expired, please run it again"* |
| `METHOD_NOT_ALLOWED` | 405 | The path exists with other methods; the `Allow` header lists them |
| `REQUEST_TOO_LARGE` | 413 | The request body is over the limit (§13) |
| `TOO_MANY_RUNS` | 429 | `CASERUNNER_MAX_RUNS` runs are all still in progress (§15.6) |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | A `POST` to `/api/` that is not `application/json` (§13 item 8) |
| `INTERNAL` | 500 | Unexpected server error, including a recovered panic |

### 15.2 `POST /api/parse`

Request:
```json
{ "curl": "curl -X POST 'https://...' -H 'Content-Type: application/json' -d '{...}'" }
```
Response 200:
```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json", "insecure": false },
  "fields": [
    { "path": "data.amount", "type": "number", "sampleValue": "100000" }
  ],
  "warnings": []
}
```

- `headers`, `fields` and `warnings` are always arrays, never `null`.
- `fields` is empty unless `bodyKind` is `json`.
- Header values are returned unmasked, because the FE sends the template back in `POST /api/runs`; the FE masks them on screen (§16).
- `type` is one of `string`, `number`, `boolean`, `null`, `object`, `array`.

### 15.3 `POST /api/runs`

The BE is stateless between parse and run: the FE sends the whole template again (the BE does not need to remember the parse result).

```json
{
  "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json" },
  "fields": [
    { "path": "data.amount",     "type": "number", "rule": "REQUIRED" },
    { "path": "data.note",       "type": "string", "rule": "UNREQUIRED" }
  ],
  "cases": [
    {
      "no": 1,
      "name": "Valid transfer",
      "values": { "data.amount": "50000", "data.note": "" },
      "expect": "\"code\":\"00\""
    }
  ],
  "prepare": {
    "steps": [ { "template": { "method": "POST", "url": "...", "headers": [...], "bodyRaw": "...", "bodyKind": "json" }, "captures": [ { "var": "token", "path": "" } ] } ],
    "injectToken": true
  },
  "options": { "concurrency": 5, "timeoutMs": 30000 }
}
```
`prepare` is optional; when it has steps, `concurrency` is ignored and cases run one at a time (D21).

Response `202`:
```json
{ "runId": "r_8f3a...", "total": 1, "blocked": 0 }
```

### 15.4 Result model

```go
type CaseStatus string // SUCCESS | FAILED | EXCEPTION | BLOCKED | CANCELLED | PENDING | RUNNING

type CaseResult struct {
    CaseIndex      int               `json:"caseIndex"`
    CaseNo         int               `json:"caseNo"`                   // the # shown in the case table (§8.1)
    Name           string            `json:"name"`
    Status         CaseStatus        `json:"status"`
    Reason         string            `json:"reason"`
    Errors         []ValidationError `json:"errors,omitempty"`     // when BLOCKED
    ErrorType      string            `json:"errorType,omitempty"`  // when EXCEPTION
    Input          map[string]string `json:"input"`
    RequestBody    string            `json:"requestBody,omitempty"`
    Expect         string            `json:"expect"`
    FoundIn        string            `json:"foundIn,omitempty"`        // status | header | body; empty when not found
    HTTPStatus     int               `json:"httpStatus,omitempty"`
    ResponseBody   string            `json:"responseBody,omitempty"`
    Truncated      bool              `json:"truncated,omitempty"`
    StartedAt      time.Time         `json:"startedAt"`
    DurationMs     int64             `json:"durationMs"`
}

type ValidationError struct {
    Field   string `json:"field"`
    Code    string `json:"code"`    // REQUIRED_MISSING | TYPE_MISMATCH | INVALID_EXPECTATION | UNKNOWN_VARIABLE
    Message string `json:"message"`
}

type Run struct {
    ID        string
    Status    string        // RUNNING | DONE | CANCELLED
    CreatedAt time.Time
    Template  RequestTemplate
    Fields    []FieldRule
    Results   []CaseResult  // index = caseIndex
    Summary   Summary       // counts by status
    mu        sync.Mutex
    cancel    context.CancelFunc
}
```

### 15.5 SSE events

```
event: snapshot      # sent immediately on connect: the full current state
data: {"runId":"...","status":"RUNNING","results":[...],"summary":{...}}

event: case          # whenever a case has a result
data: {CaseResult}

event: done
data: {"runId":"...","status":"DONE","summary":{"total":10,"success":6,"failed":2,"exception":1,"blocked":1,"cancelled":0}}
```

- Sending `snapshot` first means a client that connects late or reconnects loses no data. `Last-Event-ID` is not needed.
- Send a `: ping` heartbeat comment every 15s so proxies (Nginx) do not cut the connection. Headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
- Publishing must not block workers: each subscriber has a buffered channel; when it is full, drop that subscriber (the client will reconnect and receive a snapshot).

### 15.6 RunStore

- `map[string]*Run` + `sync.RWMutex`.
- Default TTL of **1 hour** after a run finishes (`CASERUNNER_RUN_TTL`). A janitor goroutine cleans up every minute.
- At most **50 runs** in memory. When exceeded, delete the oldest DONE run. If all are RUNNING → `429 TOO_MANY_RUNS`.
- Expired run → `GET` / `events` / `cancel` / `export` return `404 RUN_NOT_FOUND` *"Run has expired, please run it again"*.

### 15.7 `POST /api/prepare/try`

Runs the prepare steps once, in order, with the policy of §13 (allowlist, `-k`, timeout clamped to `CASERUNNER_MAX_TIMEOUT_MS`).

Request:
```json
{
  "steps": [
    { "template": { "method": "POST", "url": "https://uat-api.example.com/auth/login", "headers": [...], "bodyRaw": "...", "bodyKind": "json", "insecure": false },
      "captures": [ { "var": "token", "path": "" } ] }
  ],
  "options": { "timeoutMs": 30000 }
}
```
Response 200 (also when a step fails; the failure is in the step):
```json
{
  "steps": [
    { "status": "OK", "httpStatus": 200, "durationMs": 182, "reason": "",
      "captured": [ { "var": "token", "path": "data.accessToken", "value": "eyJ..." } ],
      "responseBody": "{...}", "truncated": false }
  ],
  "vars": { "token": "eyJ..." }
}
```
- `status`: `OK`, `FAILED` (with `reason` and, when no response was received, `errorType`), or `SKIPPED` (an earlier step failed).
- `path` is the path the value was read from, which shows where the automatic token search found it.
- At most 10 steps per request; the request body is limited to 2 MB like `/api/parse`.

**4. Test cases panel** (right column, only for a JSON body; a card with the case count, the blocked count and the run options, and **Edit test cases**, which opens the table in a large modal with **Close** and **Run**):
- **Case table** (§8): one pre-filled row after Analyze, **`+ Add case`** for more, Duplicate / Delete per row; the `expect` cell is required; paginated by 50 rows.
- FE pre-validation: an empty Required cell or expect is highlighted red with a tooltip (D4, D15), and a line counts the cases that will be blocked. Running is still allowed, after the confirmation *"X case(s) will be blocked"*.
- Run options: parallel requests (1–20; fixed at 1 with token steps, D21), timeout (1–120 seconds).
- **Run** is in the top bar. **Export config** saves `{version:1, prepare, curl, rules, cases, options}` (never captured values); **Import config** restores it and analyzes the curls again.

**5. Results panel** (below the case table; empty until the first run):
- A `Progress` bar (finished / total) and a status filter with counts (SUCCESS green / FAILED red / EXCEPTION orange / BLOCKED / CANCELLED); results arrive one by one over SSE.
- `Table` sorted by case number: #, Name, Expect, HTTP, Status (colored `Tag`), Duration, Reason; a status filter. Clicking a row opens a `Drawer` with the status, reason, where the code was found, the values sent, the request body and the response body with the expect code highlighted.
- **Cancel run** while running, **Run again** afterwards, both in the top bar (same configuration; replaces the results).
- Persistent note: results are kept in memory for a limited time (1 hour by default) and lost when the tool restarts. Excel/PDF export comes with Step 10.

## 19. Testing

- **Unit**: the `domain` packages (curl, field, testcase, run classifier). This is where the business rules live and needs the most thorough testing.
- **Use case**: `usecase` with in-memory fakes of its ports (worker pool, cancel, limits).
- **Integration**: `adapter/sender` + `httptest.Server`; `adapter/httpapi` handlers with `httptest.NewRecorder`.
- **Race**: always run `go test -race ./...` (worker pool, memstore, broker).
- **Manual E2E**: FE + BE + mockapi, 50 cases, concurrency 5, with a few BLOCKED/timeout cases.

Critical cases that must not be missed:
1. Required field left empty → BLOCKED, and **no** request reaches the fake server (count hits).
2. Unrequired field left empty → the request does **not contain** that key.
3. Large numbers / amounts keep full precision in the sent request.
4. Timeout → EXCEPTION/TIMEOUT, **no** retry (the fake server receives exactly 1 hit).
5. The number of concurrent requests never exceeds `concurrency`.
6. A panic in one case does not crash the run.
7. Cancelling a run midway → cases not yet started are CANCELLED.
8. Expect is a substring search over status, headers and body: `ERR_X` in the body → SUCCESS whatever the HTTP status; `401` as the status → SUCCESS; a missing code → FAILED.
10. With prepare steps, every case gets a newly captured token (`/secure` sees a different token per case), and a failed login makes only that case `PREPARE_FAILED`.
9. A row added with `+` and left unchanged produces a request identical to the curl's original body.

## 21. Build and run

`caserunner/scripts/build.sh` builds the frontend (`npm ci` on first use, then `npm run build`), copies `frontend/dist` into `backend/internal/adapter/web/dist`, and builds `backend/bin/caserunner` with the version from `VERSION` (default `dev`). Running that one binary serves the UI and the API at `http://127.0.0.1:8080` (`CASERUNNER_BIND`). `--run` starts it right after the build; an API Case Runner already listening on the port is stopped first (Ctrl+C, then a hard stop after 10 s), while any other program on the port fails the build without being touched. `scripts/build.ps1` (with `-Run`) does the same on Windows and writes `backend\bin\caserunner.exe`; `GOOS=windows GOARCH=amd64 scripts/build.sh` cross-builds that `.exe` from Linux.

A binary built with plain `go build`, without the script, still serves the API; `/` then answers `503` with a note that the frontend is not built. During development the Vite dev server (`npm run dev`, port 5173) proxies `/api` to the backend (`CASERUNNER_API_URL`, default `http://127.0.0.1:8080`).

| Tool | Version |
|---|---|
| Go | 1.27+ |
| Node.js | 20.19+ or 22.12+ (build only) |
| gcc | for `go test -race` only |
